Read this for keyboard access, screen readers, OS display settings (contrast, motion, transparency, text size), contrast, target sizes, and the legal baseline (WCAG 2.2 via WCAG2ICT, EN 301 549, EAA, Section 508). Units: pt on macOS, epx on Windows, px on the web stack. Every rule cites its source inline; ⚠️ marks claims that couldn't be fully verified (collected at the end). Researched November 2026 — platform details change, so re-check anything version-specific.

## 0. Key thresholds (desktop units: **pt** macOS, **epx** Windows; WCAG "CSS px" ≈ these; 1 typographic pt = 1.333 CSS px)

| Topic | Number | Level / source |
|---|---|---|
| Text contrast | **4.5:1**; large text (≥ 24 px/pt/epx regular or ≥ 18.5 bold; WCAG's "18 pt / 14 pt" are typographic points, so Mac's 13 pt body is *normal* text) **3:1**; AAA 7:1 / 4.5:1 | WCAG 1.4.3 AA / 1.4.6 AAA |
| UI component & graphics contrast | **3:1** vs adjacent colors (borders, icons, focus rings, chart marks) | 1.4.11 AA |
| Focus indicator (design spec) | area ≥ **2 px perimeter** of the control; **3:1** focused-vs-unfocused; 2 px inset ring fails, 3 px passes | 2.4.13 AAA |
| Focus not obscured | not **fully** hidden (AA) / not even partly (AAA) | 2.4.11 / 2.4.12 |
| Target size | **24×24** min (or 24-unit circle spacing → 20 pt targets need 4 pt gaps); 44×44 AAA | 2.5.8 AA / 2.5.5 AAA |
| Platform control size | macOS **28×28 pt default, 20×20 min**, padding ~12 pt bezelled / ~24 pt borderless; Windows touch **40×40 epx** (7.5 mm), dense mouse ≥32 | Apple HIG; MS Learn |
| Text resize | **200 %** (own zoom or OS setting as far as it goes); Windows Text size **100–225 %**; macOS has **no** Dynamic Type | 1.4.4 + WCAG2ICT; MS Learn; HIG |
| Mac text sizes | default **13 pt**, min **10 pt** (11 pt secondary) | HIG |
| Smallest text (best practice) | x-height ≥ **8 CSS px** (1.2 mm at 400 mm) | EN 301 549 11.1.4.4 Note 4 |
| Reflow | usable at **320** wide (vertical scroll) / **256** tall; toolbars, tables, canvases exempt | 1.4.10 AA + EN Notes |
| Text spacing (markup UIs incl. Electron/XAML) | line 1.5×, paragraph 2×, letter 0.12×, word 0.16× without loss — only if users can change spacing | 1.4.12 + WCAG2ICT Note 1/4 |
| Flashing | ≤ **3 / s**; area < 25 % of 10° ≈ **341×256 px @1024×768** | 2.3.1 A |
| Moving/blinking content | pause/stop/hide if > **5 s** | 2.2.2 A |
| Time limits | turn off / ≥ **10×** / warn + ≥ **20 s**, extend ≥10 times; > **20 h** exempt | 2.2.1 A |
| Contrast themes | palettes "typically at or above **7:1**"; **4** built-in Windows themes | MS Learn |

## 1. Law & standards (2026)

**Agent default: build to WCAG 2.2 AA + EN 301 549 clause 11 (software) + "follow the OS accessibility settings".** That one target covers EU, US federal and US state/local baselines.

- **WCAG 2.2** is the current W3C Rec (5 Oct 2023, updated 12 Dec 2024); it is **ISO/IEC 40500:2025**, and W3C expects the Dec 2024 text as ISO/IEC 40500:2026 "by late 2026". 4.1.1 Parsing is obsolete. Page updated 17 Sep 2026. [W3C WCAG overview](https://www.w3.org/WAI/standards-guidelines/wcag/)
- **WCAG 3** is still a **Working Draft (10 Sep 2026)**; the draft itself says it "still has several years of work". Don't use WCAG 3 / APCA as a pass/fail requirement. [WCAG 3 WD](https://www.w3.org/TR/wcag-3.0/)
- **WCAG2ICT** (W3C Group Note, **11 Dec 2025**) is how WCAG maps to desktop software. [WCAG2ICT](https://www.w3.org/TR/wcag2ict-22/)
  - "web page" → **"software program"**; "set of web pages" → **"set of software programs"** (separately launchable programs, same author, all interlinked by a consistent switcher). The Note says such sets "appear to be extremely rare", and any program not in a set **automatically satisfies** 2.4.1, 2.4.5, 3.2.3, 3.2.4, 3.2.6. Don't rely on that loophole for UX: consistency is still good design. [WCAG2ICT key terms](https://www.w3.org/TR/wcag2ict-22/#set-of-software-programs)
  - **"CSS pixel" → platform density-independent unit: pt (macOS), epx (Windows effective pixels), dp (Android)**. 1 typographic pt = 1.333 CSS px. [WCAG2ICT CSS pixel](https://www.w3.org/TR/wcag2ict-22/#applying-css-pixel-to-non-web-documents-and-software)
  - **2.4.2 Page Titled → "Non-web Software Titled"**: every window/dialog has a title describing name, topic or purpose. [WCAG2ICT 2.4.2](https://www.w3.org/TR/wcag2ict-22/)
  - **1.4.4 Resize Text**: 200 % "zoom or otherwise", *or* follow the platform text-size setting as far as the platform goes. **1.4.10 Reflow**: applies when users "adjust the size of a window, dialog, or other resizable content area, or change the screen resolution"; toolbars that must stay visible are an accepted 2-D exception. **4.1.3 Status messages**: met through "accessibility services of the user agent or other platform software" (i.e. UIA/NSAccessibility/AT-SPI events). [WCAG2ICT](https://www.w3.org/TR/wcag2ict-22/)
  - **2.1.4**: a long key press (≥2 s) and platform accessibility features are *not* "keyboard shortcuts". [WCAG2ICT 2.1.4](https://www.w3.org/TR/wcag2ict-22/)
- **EN 301 549 V4.1.1 (2026-09)** — published **2 Sep 2026**; clauses 9/10/11 now reference **WCAG 2.2 AA**. **Not yet cited in the EU Official Journal** on 2026-11-02, so **V3.2.1 (WCAG 2.1) is still the legal presumption-of-conformity baseline**; expected citation dates differ (Deque: "around 30 Nov 2026"; Ireland's NDA: "16 Dec 2026") ⚠️. [ETSI PDF](https://www.etsi.org/deliver/etsi_en/301500_301599/301549/04.01.01_60/en_301549v040101p.pdf), [NDA](https://nda.ie/news/en301549-published), [Deque](https://www.deque.com/de/blog/en-301-549-v4-1-1-is-final-what-changed-what-it-means-and-what-you-should-do/)
  - **Clause 11 (non-web software) in V4.1.1**, read from the ETSI PDF: includes 11.2.4.11 Focus not obscured, 11.2.5.7 Dragging, 11.2.5.8 Target size (24 CSS px), 11.3.3.7 Redundant entry, 11.3.3.8 Accessible authentication. **Void for software**: 2.4.1 Bypass blocks, 2.4.5 Multiple ways, 3.1.2 Language of parts, 3.2.3 Consistent navigation, **3.2.6 Consistent help** ("sets of non-web software … are extremely rare"). 2.4.2 is replaced by **11.2.4.2 Non-web software titled**.
  - 11.1.4.4 Note 4: best practice smallest text **x-height ≥ 8 CSS px (1.2 mm at 400 mm)**.
  - **11.5.2.x** = what your accessibility tree must expose (object info, row/column headers, values, label & parent-child relations, text, actions, focus/selection tracking, change notifications). 11.5.2.3 "Use of accessibility services" is now worded as a **recommendation** ("should"; NOTE: use toolkits that implement platform services automatically) ⚠️ (I believe V3.2.1 used "shall"; not re-checked).
  - **11.6.2 No disruption of accessibility features**: don't break platform AT features (e.g. don't swallow VoiceOver/Narrator keys, don't block magnifier tracking) unless the user asks.
  - **11.7 User preferences**: software "shall follow the values of the user preference settings for documented platform accessibility features" (colour filters, contrast, text size, pointer size, text cursor) unless essential; an extra in-app value is fine **as long as one mode follows the system**. Apps "isolated from the platform" are exempt — but an Electron/Flutter app *can* read these settings, so assume you are in scope.
  - 12.3: product docs must link to accessibility-feature info ("Accessibility info at vendor.com/accessibility").
- **European Accessibility Act** (Directive 2019/882) — applies to products placed on the market and services provided **after 28 June 2025**. [Art. 2](https://www.legislation.gov.uk/eudr/2019/882/article/2) (EUR-Lex text mirror)
  - Products: consumer general-purpose computers **and their operating systems**, self-service terminals, consumer terminals for e-communications and audiovisual media, e-readers.
  - Services: electronic communications, access to audiovisual media, passenger-transport elements, **consumer banking**, **e-books and dedicated software**, **e-commerce**.
  - **A generic consumer desktop app (editor, game, utility) is *not* covered by itself.** It *is* covered when it is the client for a covered service: messaging/calling apps, streaming/TV apps, banking apps, e-book readers, shop apps. Note the e-commerce definition says "through websites and mobile device-based services" — a desktop-only shop client is a grey zone ⚠️. [Art. 3](https://www.legislation.gov.uk/eudr/2019/882/article/3)
  - **Microenterprises providing services** (<10 staff and ≤ €2 M turnover or balance sheet) are exempt from service requirements (Art. 4(5)). Transition: services may keep using previously-used products until **28 June 2030** (Art. 32). [Art. 4](https://www.legislation.gov.uk/eudr/2019/882/article/4), [Art. 32](https://www.legislation.gov.uk/eudr/2019/882/article/32)
- **US Section 508** (federal procurement): software must meet **WCAG 2.0 A/AA** (E207.2; 2.4.1, 2.4.5, 3.2.3, 3.2.4 excluded for non-web software) **plus 502/503**: **503.2 "Applications shall permit user preferences from platform settings for color, contrast, font type, font size, and focus cursor"**; 502.3 lists the AT-API surface (object info, values, label relationships, actions, focus cursor, event notification). [Access Board ICT](https://www.access-board.gov/ict/)
- **ADA Title II rule** (state & local government web content **and mobile apps**): **WCAG 2.1 AA**. A 2026 Interim Final Rule moved compliance to **26 Apr 2027** (≥50,000 population) and **26 Apr 2028** (smaller entities, special districts). It does not name desktop apps; the DOJ rule directs implementers to WCAG2ICT to apply WCAG to mobile apps (so expect WCAG2ICT readings for any app). [ADA.gov](https://www.ada.gov/resources/2024-03-08-web-rule/), [WCAG2ICT intro](https://www.w3.org/TR/wcag2ict-22/)

## 2. Keyboard

**Rule zero: every feature reachable and operable from the keyboard alone, with a visible focus indicator, in a sensible order, with no traps.** Desktop users include power users, screen-reader users (who drive *everything* by keyboard) and switch / voice users whose tools emit keystrokes.

### 2.1 WCAG requirements (all apply "directly as written" to software per WCAG2ICT)
- **2.1.1 Keyboard (A)**: all functionality via keyboard, no timing-dependent keystrokes (path-dependent drawing is the only exception). Drag-and-drop, hover-only toolbars, canvas selection, resize handles and column reordering all need a keyboard path (menu command, arrow-key nudge, "Move to…" dialog). [WCAG 2.2](https://www.w3.org/TR/WCAG22/#keyboard)
- **2.1.2 No Keyboard Trap (A)**: Tab/Shift+Tab/Esc must always get out. Classic desktop traps: code editors/terminals that eat Tab (offer Ctrl+M / Esc-then-Tab like VS Code's "Toggle Tab Key Moves Focus" ⚠️ name from memory), embedded web views/plug-ins, custom canvases. If leaving needs a non-standard key, tell the user. [WCAG 2.2](https://www.w3.org/TR/WCAG22/#no-keyboard-trap)
- **2.1.4 Character Key Shortcuts (A)**: single-key shortcuts (letters, digits, punctuation, e.g. "J/K", "E" to archive, "/" to search) need **one of**: a way to turn them off, a way to remap them to include Ctrl/Alt/⌘, or they only work while that component has focus. *Why:* speech-input users dictating text trigger them by accident. WCAG2ICT: long-press ≥2 s isn't a shortcut. [WCAG 2.2](https://www.w3.org/TR/WCAG22/#character-key-shortcuts), [WCAG2ICT](https://www.w3.org/TR/wcag2ict-22/)
- **2.4.3 Focus Order (A)**: order follows reading/visual flow. In WinUI default order = XAML declaration order; `TabIndex` sorts ascending (negative < 0 < positive < unset = Int32.MaxValue), ties keep declaration order — MS example: A, B(MaxValue), C, D(1), E(1), F(0) → **F, D, E, A, B, C**. Prefer fixing markup order over TabIndex. [MS Learn keyboard accessibility](https://learn.microsoft.com/en-us/windows/apps/design/accessibility/keyboard-accessibility)
- **2.4.7 Focus Visible (AA)**: never `outline: none` / `UseSystemFocusVisuals="False"` without a replacement. **2.4.11 Focus Not Obscured (Min, AA)**: focused item not *entirely* hidden by your own sticky headers, floating toolbars, toasts, cookie bars, docked panels — scroll it into view with padding (`scroll-padding`, `BringIntoView`, `scrollRectToVisible`). User-moved panels only count at their initial position. **2.4.12 (AAA)**: not even partly hidden. [WCAG 2.2](https://www.w3.org/TR/WCAG22/#focus-not-obscured-minimum), [WCAG2ICT](https://www.w3.org/TR/wcag2ict-22/)
- **2.4.13 Focus Appearance (AAA, but use it as your design spec)**: indicator area ≥ a **2 CSS px thick perimeter** of the unfocused component **and** ≥**3:1** change-contrast between the same pixels focused vs unfocused. Perimeter ≈ `4h + 4w` (rounded rect: `4h+4w−(16−4π)r`). A solid **2 px outline outside or on the edge passes; a 2 px *inset* outline fails (needs ≥3 px)**. Also meet **1.4.11** (indicator ≥3:1 against adjacent colors). Easiest: two-tone ring (e.g. 2 px accent + 1 px contrasting halo) with `outline-offset: 2px`. Exempt only if you leave the platform focus ring and its background untouched. [Understanding 2.4.13](https://www.w3.org/WAI/WCAG22/Understanding/focus-appearance.html), [WCAG 2.2](https://www.w3.org/TR/WCAG22/#focus-appearance)

### 2.2 Composite widgets: one Tab stop, arrows inside (ARIA APG = de-facto desktop conventions)
- "The tab sequence should include only one focusable element of a composite UI component"; arrows move within. On re-entry: last-focused (grid/treegrid), selected-or-first (tabs, listbox, tree, radio), first (menubar, toolbar). [APG keyboard interface](https://www.w3.org/WAI/ARIA/apg/practices/keyboard-interface/)
- **Roving tabindex** (active item `tabindex=0`, rest `-1`, call `.focus()`; browser auto-scrolls it into view) vs **`aria-activedescendant`** (DOM focus stays on the container, which points to the active child's id; child must be a descendant or `aria-owns`ed). Prefer roving tabindex; use activedescendant for virtualised lists/comboboxes where moving DOM focus is costly — then scroll the active item into view yourself. [APG](https://www.w3.org/WAI/ARIA/apg/practices/keyboard-interface/)
- **Focus ≠ selection**: one focus point; selected state must look different from focus. Don't make selection follow focus when selecting is expensive (network load) — require Enter/Space. **Disabled menu items, options, tabs, tree items stay focusable** (`aria-disabled`) so they're discoverable. [APG](https://www.w3.org/WAI/ARIA/apg/practices/keyboard-interface/)

| Widget | Keys (APG) | Roles/props (web) |
|---|---|---|
| **Menubar/menu** [APG](https://www.w3.org/WAI/ARIA/apg/patterns/menubar/) | ←/→ across bar; ↓/Enter/Space opens submenu (focus 1st item); ↑/↓ in menu; → opens submenu, ← closes it; Home/End; Esc closes & returns focus to opener; Tab leaves and closes all; printable char jumps to next item starting with it | `menubar`, `menu`, `menuitem`/`menuitemcheckbox`/`menuitemradio` + `aria-checked`, `aria-haspopup="menu"`, `aria-expanded`; separators not focusable |
| **Toolbar** [APG](https://www.w3.org/WAI/ARIA/apg/patterns/toolbar/) | One Tab stop; ←/→ (↑/↓ if vertical); Home/End optional; at most one arrow-hungry control (text field), placed **last**; only use for **≥3 controls**; give a documented shortcut to jump into an editor toolbar | `toolbar` + `aria-label`, `aria-orientation` |
| **Tree** [APG](https://www.w3.org/WAI/ARIA/apg/patterns/treeview/) | ↑/↓ move; → expand / go to first child; ← collapse / go to parent; Home/End; Enter = default action; type-ahead; `*` expands siblings; multi: Space toggles, Shift+↑/↓ extend, Ctrl+A | `tree`, `treeitem`, `group`, `aria-expanded` (parents only), `aria-selected`, `aria-level/setsize/posinset` when lazy-loaded |
| **Grid** (file lists, spreadsheets, tables with actions) [APG](https://www.w3.org/WAI/ARIA/apg/patterns/grid/) | Arrows by cell; Home/End row; Ctrl+Home/End grid; PgUp/PgDn; Enter or **F2** edits cell, Esc cancels; Ctrl+Space column, Shift+Space row, Shift+arrows extend | `grid`, `row`, `gridcell`, `columnheader`/`rowheader`, `aria-rowcount/rowindex` (virtualised), `aria-readonly`, `aria-selected` |
| **Listbox** [APG](https://www.w3.org/WAI/ARIA/apg/patterns/listbox/) | ↑/↓; Home/End (strongly recommended >5 items); **type-ahead recommended, esp. >7 items**; multi like tree. Never put buttons/links inside options — use a grid | `listbox`, `option`, `aria-multiselectable`, `aria-selected` |
| **Tabs** [APG](https://www.w3.org/WAI/ARIA/apg/patterns/tabs/) | Tab enters active tab, next Tab goes to panel; ←/→ wrap; Home/End; **automatic activation only if panels show instantly**, else Space/Enter; Delete closes (optional); Shift+F10 tab menu | `tablist`, `tab` + `aria-selected` + `aria-controls`, `tabpanel` + `aria-labelledby` (+`tabindex=0` if no focusable content) |

- Native toolkits (NSTableView/NSOutlineView, WinUI ListView/TreeView, GtkListView/GtkColumnView, Qt item views) implement these for free; **custom-drawn lists are where keyboard support dies**. macOS 27 adds `NSSegmentedControl.role = .tabs` and SwiftUI `TabsPickerStyle`, which VoiceOver reads as "tabs" — use them when a segmented control switches views. [macOS 27 release notes](https://developer.apple.com/documentation/macos-release-notes/macos-27-release-notes)

### 2.3 Desktop navigation conventions
- **F6 / Shift+F6 cycles major panes** (sidebar → content → inspector → toolbar). Windows: "You must implement F6 navigation explicitly in your app; it is not provided automatically"; name each region (`AutomationProperties.Name`). Do it on all platforms; it's cheap. [MS Learn](https://learn.microsoft.com/en-us/windows/apps/design/accessibility/keyboard-accessibility)
- **Esc** closes the innermost transient surface (menu, popover, dialog, inline edit) and returns focus to what opened it. **Return** activates, **Space** toggles. **Shift+F10 / Menu key** opens the context menu for the focused item (Windows, GNOME, APG). **F10** opens the primary/hamburger menu on GNOME. [GNOME HIG keyboard](https://developer.gnome.org/hig/guidelines/keyboard.html), [APG](https://www.w3.org/WAI/ARIA/apg/practices/keyboard-interface/)
- **Access keys/mnemonics** (Windows, GNOME, KDE): Alt + underlined letter. GNOME: first letter, else a memorable consonant; avoid i, l, g, y; re-check after translation; **don't use Alt for accelerators**; never bind **Super**. WinUI: `AccessKey`, and expose metadata with `AutomationProperties.AccessKey` / `AcceleratorKey` (these only *describe* keys, they don't implement them). [GNOME HIG](https://developer.gnome.org/hig/guidelines/keyboard.html), [MS Learn](https://learn.microsoft.com/en-us/windows/apps/design/accessibility/keyboard-accessibility)
- **Don't steal AT/OS keys**: no shortcuts on Caps Lock/Insert/Scroll Lock combos (NVDA/JAWS/Narrator modifiers), **Ctrl+Option on macOS (VoiceOver)**, modifier+Tab/Enter/Space/Esc, Meta/Win+single key, Alt+F-keys. macOS: ⌃F1 (Full Keyboard Access), ⌃F2 (menu bar), ⌃F3 (Dock), ⌃F4 (next window), ⌘F5 (VoiceOver) are system-owned. [APG](https://www.w3.org/WAI/ARIA/apg/practices/keyboard-interface/), [Apple HIG Keyboards](https://developer.apple.com/design/human-interface-guidelines/keyboards)
- **Type-ahead** in every list, tree, table and menu longer than ~7 items. [APG listbox](https://www.w3.org/WAI/ARIA/apg/patterns/listbox/)
- **Shortcut discoverability**: show accelerators in menus and tooltips ("Copy (Ctrl+C)"); provide a shortcuts sheet (GNOME Ctrl+?, macOS menu bar = the index).

### 2.4 macOS focus is different (don't "fix" it)
- By default macOS **Tab reaches only text fields and lists**; buttons, pop-ups, checkboxes join the loop only when the user enables **Keyboard navigation** (System Settings › Keyboard; ⌃F7) or **Full Keyboard Access** (Accessibility › Keyboard; ⌃F1). HIG: "you only need to support focus for content elements like list items, text fields, and search fields, and not for controls like buttons, sliders, and toggles" — the system handles those when the user opts in. Test **both** modes. [Apple HIG Focus and selection](https://developer.apple.com/design/human-interface-guidelines/focus-and-selection), [Apple HIG Keyboards](https://developer.apple.com/design/human-interface-guidelines/keyboards)
  - AppKit: custom views opt in with `acceptsFirstResponder`/`canBecomeKeyView` and respect `NSApp.isFullKeyboardAccessEnabled`; SwiftUI: `.focusable()`, `@FocusState`, `.focusSection()` ⚠️ (API names from memory, not re-checked).
  - macOS 27 fixed a bug where the key loop skipped fields with keyboard navigation off — so test on 27. [macOS 27 release notes](https://developer.apple.com/documentation/macos-release-notes/macos-27-release-notes)
- Use the system focus ring (accent-colored, follows Increase Contrast) and list highlight (accent when focused, gray when not); custom focus effects only if "absolutely necessary". [HIG Focus](https://developer.apple.com/design/human-interface-guidelines/focus-and-selection)
- **Windows & Linux**: every interactive control *is* a Tab stop by default — do make buttons focusable there. Electron/web apps must decide per OS (see cross-platform.md).

## 3. Screen readers & platform accessibility APIs

**Model: every element exposes name, role, value/state, relationships and actions through the OS API (UIA / NSAccessibility / AT-SPI); changes fire events.** That's WCAG 4.1.2 + 4.1.3 and EN 301 549 11.5.2.5–17. Standard toolkit controls do this; each custom-drawn control is a debt.

| OS | Screen readers to test | API your toolkit talks |
|---|---|---|
| macOS | VoiceOver (built-in) | NSAccessibility (AppKit), SwiftUI accessibility modifiers |
| Windows | **NVDA** (free), **Narrator** (built-in), JAWS (paid, common in enterprise) | UI Automation (UIA); browsers/Chromium also expose MSAA/IAccessible2 |
| Linux | **Orca** | AT-SPI2 over D-Bus (GTK4, Qt, Chromium, Avalonia 12) |

### 3.1 Universal rules
- **Name**: short, visible-label-matching (2.5.3 Label in Name), no role word ("Save", not "Save button" → "Save button button"; MS: "do not repeat role/type terms"). Icon-only buttons need *both* a tooltip and an accessible name — a tooltip is not reliably the name. Localize names like any UI string. [MS Learn basic a11y info](https://learn.microsoft.com/en-us/windows/apps/design/accessibility/basic-accessibility-information)
- **Description/help text** = optional extra (Narrator reads it on demand, Caps Lock+F). Keep names ≤ a few words; UIA truncates names at **2048 chars**. [MS Learn](https://learn.microsoft.com/en-us/windows/apps/design/accessibility/basic-accessibility-information)
- **Label fields by reference** to the visible label (`LabeledBy`, `GTK_ACCESSIBLE_RELATION_LABELLED_BY`, `Accessible.labelledBy` (Qt 6.10), `<label for>`/`aria-labelledby`, SwiftUI `.accessibilityLabeledPair`) so spoken and visible text can't drift.
- **Hide decoration and layout wrappers** (`AccessibilityView="Raw"`, `GTK_ACCESSIBLE_ROLE_PRESENTATION`/`GENERIC`, `Accessible.ignored`, `aria-hidden`, `.accessibilityHidden(true)`); **group** row parts into one element (`.accessibilityElement(children: .combine)`; default for the modifier is `.ignore`). [Apple accessibilityElement(children:)](https://developer.apple.com/documentation/swiftui/view/accessibilityelement(children:))
- **Window/dialog titles** are the "page title" for software (EN 301 549 11.2.4.2): set a real `title` on every window, sheet and dialog even if the title bar is hidden/custom ("Invoice 1042 — Acme", not "Acme").
- **Headings & landmarks/regions**: name sidebar, content and inspector regions; mark section headings (`.accessibilityHeading(.h2)` speaks the level; `AutomationProperties.HeadingLevel`; `role="heading" aria-level`). [Apple accessibilityHeading](https://developer.apple.com/documentation/swiftui/view/accessibilityheading(_:))
- **Tables/lists expose rows, columns, headers, counts, selection** (EN 301 549 11.5.2.6/.13). Virtualised lists: expose total count/position (`aria-rowcount`/`aria-setsize`, `aria-posinset`).
- **Custom actions instead of hover-only buttons**: expose row actions (Delete, Pin) as accessibility actions (`.accessibilityAction(named:)`, UIA patterns/context menu, `aria-` + context menu) — and as menu items.

### 3.2 Announcing async results (4.1.3 Status messages)
Use for: "Saved", "Export finished", "3 results", "Connection lost", validation summaries, progress milestones. **Don't move focus to announce. Don't announce every keystroke or every % of progress.** Prefer *polite/medium*; use *assertive/high* only for errors that block the user.

| Stack | API (verified) | Notes |

### 4.2 What each setting should change
- **Increase Contrast / prefers-contrast: more**: darker secondary text (aim 7:1), solid ≥1 px separators at ≥3:1, borders on cards/inputs/buttons, opaque sidebars, thicker focus ring. Use system/semantic colors (they have high-contrast variants automatically); add Asset Catalog "High Contrast" variants for custom colors. HIG: if default contrast is below WCAG AA, "at least provide a higher contrast color scheme when … Increase Contrast is turned on". [HIG Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility)
- **Show borders (macOS 27)**: draw visible edges on custom borderless/glass buttons, toolbar items and form sections (Apple even fixed `.grouped` Form sections to honor it). [macOS 27 notes](https://developer.apple.com/documentation/macos-release-notes/macos-27-release-notes)
- **Windows contrast themes** (Aquatic, Desert, Dusk, Night sky; Left Alt+Left Shift+PrtScn toggles; palettes "typically at or above 7:1"; users edit colors): [MS Learn](https://learn.microsoft.com/en-us/windows/apps/design/accessibility/high-contrast-themes)
  - XAML: `ThemeDictionaries` with `Default`, `Light`, **`HighContrast`**; in HighContrast map brushes only to `SystemColor*` pairs: `WindowColor`+`WindowTextColor` (surfaces/text), `HotlightColor` (links only), `GrayTextColor` (**disabled only — never secondary text**), `HighlightColor`+`HighlightTextColor` (selected/hover/pressed), `ButtonFaceColor`+`ButtonTextColor` (interactive). Use `{ThemeResource}` (two-stage lookup) so switching is live. Set `HighContrastAdjustment="None"` only once your resources are right. **2 px borders** on flyouts/dialogs; contrast-only borders between same-colored panes; don't hard-set `Foreground` inside ListView item templates (breaks selection inversion).
  - **Test all four themes while the app is running.**
  - Web/Electron (`forced-colors: active`): colors, borders, outlines, SVG fill/stroke are overridden; **`box-shadow` → none** (so shadow-only focus rings and card edges vanish: add `outline: 2px solid transparent` / transparent borders that become visible); background-images (gradients) → none; icons: `fill: currentColor`; use system colors `Canvas`, `CanvasText`, `LinkText`, `ButtonFace`, `ButtonText`, `Highlight`, `HighlightText`, `GrayText`; `forced-color-adjust: none` only for color swatches/previews. Forced colors pick colors by **native element semantics, not ARIA** (a `div role=button` gets text colors). [MDN forced-colors](https://developer.mozilla.org/en-US/docs/Web/CSS/@media/forced-colors)
- **Reduce transparency**: replace blur/vibrancy/Mica/acrylic/glass with opaque equivalents (system materials do this automatically; your custom `NSVisualEffectView`/CSS `backdrop-filter`/Composition blur must check). Windows Mica also falls back when the window is inactive or on battery saver — design the solid fallback first (windows.md).
- **Reduce motion**: see §8.
- **Text size**: macOS has no system text-size API for third-party apps → provide **View › Zoom In/Out/Actual Size (⌘+ / ⌘− / ⌘0)** or a text-size setting in content-heavy apps; Windows → let WinUI scale, never fix heights, wrap text, clip the *end* + tooltip if you must, don't scale glyph icons (`IsTextScaleFactorEnabled="False"`). [MS Learn text scaling](https://learn.microsoft.com/en-us/windows/apps/develop/input/text-scaling)

## 5. Pointer, targets & layout

- **2.5.8 Target Size (Min, AA)** = **24×24 pt/epx** (EN 301 549 11.2.5.8 copies it for software), or smaller with spacing: a 24-unit circle centred on each undersized target mustn't intersect another target/circle → **20 pt controls need ≥4 pt gaps; 16 pt icon buttons need ≥8 pt gaps**. Exceptions: equivalent control elsewhere, inline-in-text, size set by the platform and unmodified, essential. Sliders/colour wells/text areas count as one target. [WCAG 2.2](https://www.w3.org/TR/WCAG22/#target-size-minimum), [EN 301 549 11.2.5.8](https://www.etsi.org/deliver/etsi_en/301500_301599/301549/04.01.01_60/en_301549v040101p.pdf)
- **Platform sizes are the real target**: macOS default control **28×28 pt, min 20×20 pt**, ~12 pt padding around bezelled, ~24 pt around borderless ([HIG Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility)); Windows touch target ≈ **7.5 mm ≈ 40×40 epx**, mouse-dense ≥32 epx (windows.md); **2.5.5 (AAA) 44×44**. Hit area may exceed the visible glyph — pad the clickable region of 16 px icons to ≥24.
- **Window chrome counts**: tab close "×", sidebar disclosure triangles, table column resize handles, splitter bars, title-bar buttons in custom title bars — give them ≥24 hit areas or keyboard/menu equivalents (e.g. Ctrl+W, Window menu).
- **2.5.2 Pointer Cancellation (A)**: fire on **mouse-up inside the target**; moving off before release cancels. Down-event actions only if reversible (undo) or essential (piano keys, drawing). Native buttons already do this — custom `onMouseDown`/`PointerPressed` handlers often don't. [WCAG 2.2](https://www.w3.org/TR/WCAG22/#pointer-cancellation)
- **2.5.7 Dragging Movements (AA)**: every drag needs a single-pointer non-drag alternative (unless essential): reorder → "Move Up/Down" menu items or arrow buttons; drag-to-folder → "Move to…" menu; splitter → double-click/menu "Reset/Hide sidebar" + keyboard; slider → click on track + arrow keys; canvas move → arrow-key nudge + X/Y fields. Also expose it to keyboard (2.1.1). GNOME HIG requires *Move Up/Move Down/Remove* menus for reorderable lists. [WCAG 2.2](https://www.w3.org/TR/WCAG22/#dragging-movements), linux.md
- **2.5.1 Pointer Gestures (A)**: trackpad pinch/rotate/two-finger swipe need button/menu/shortcut equivalents (zoom buttons, ⌘+/−, Back button for swipe-back).
- **2.5.3 Label in Name (A)**: accessible name contains the visible text (Voice Control / Windows Voice Access / dictation users say what they see).
- **1.4.13 Content on Hover or Focus (AA)** — custom tooltips, hover cards, submenus, non-modal popovers must be: **Dismissible** (Esc, without moving pointer/focus), **Hoverable** (pointer can move onto it without it closing), **Persistent** (stays until hover/focus leaves, dismissed, or invalid). Also show on keyboard focus, not just hover. Native OS tooltips (`toolTip`, `ToolTipService`, `tooltip-text`, HTML `title`) are exempt as platform-controlled — but `title` never shows on keyboard focus, so don't put essential info there. [Understanding 1.4.13](https://www.w3.org/WAI/WCAG22/Understanding/content-on-hover-or-focus.html), [WCAG2ICT 1.4.13](https://www.w3.org/TR/wcag2ict-22/)
  - Hover-revealed row actions (trash icon appears on hover) → also reachable via keyboard focus, context menu (Shift+F10) and accessibility actions.
- **1.4.4 Resize Text (AA)** for software = 200 % via your own zoom **or** by following the platform text-size setting as far as it goes (WCAG2ICT/EN 11.1.4.4). **1.4.10 Reflow (AA)** for software = content reflows when users **resize the window/dialog/pane or raise display scaling**, down to ~**320 pt/epx wide**; keeping toolbars visible, data tables, canvases, timelines and editors with 2-D layout are accepted exceptions (EN Note 2/5). Practical rules: [WCAG2ICT](https://www.w3.org/TR/wcag2ict-22/), [EN 301 549 11.1.4.10](https://www.etsi.org/deliver/etsi_en/301500_301599/301549/04.01.01_60/en_301549v040101p.pdf)
  - Set a sensible **minimum window size ≤ 500 px wide** and make every window usable at it (collapse sidebars to overlays, wrap toolbars into overflow "»" menus, stack form label above field).
  - Benchmark width **320 epx/pt** = a 640-physical-px window at 200 % scaling (or 1280 px at 400 %). If your minimum window is wider, evaluate at that minimum (EN Note 6: "nearest size"). Also test Windows text size 225 %.
  - Dialogs: never fixed-size with clipped text; let them grow or scroll vertically.
- **Electron/Tauri zoom**: keep **View › Actual Size / Zoom In / Zoom Out** (Electron menu roles `resetZoom`, `zoomIn`, `zoomOut`; CmdOrCtrl+0 / + / −) — don't strip the default View menu without replacing it; persist the zoom level per window; size with `rem`/`em` so zoom and default font size both work. [Electron MenuItem roles](https://www.electronjs.org/docs/latest/api/menu-item)
- **1.3.4 Orientation**: effectively N/A on desktop, but don't lock windows to a landscape aspect ratio — portrait monitors and tiled half-screen windows are common.

## 6. Color & contrast

Compute contrast with the WCAG relative-luminance formula: run `scripts/contrast.py` instead of estimating; WCAG2ICT: 1 pt = 1.333 CSS px, so "large" = **≥18 pt regular or ≥14 pt bold (≈24/18.5 px)**. Never round (4.499 fails). [WCAG2ICT](https://www.w3.org/TR/wcag2ict-22/)

- **1.4.3 (AA)** text ≥ **4.5:1**, large ≥ **3:1**; **1.4.6 (AAA)** ≥ **7:1** / 4.5:1. Mac UI text is small (13 pt body, 11 pt secondary, 10 pt min) so **almost all desktop UI text is "normal" text → 4.5:1**. Apple's Accessibility Inspector treats ≥18 pt or any bold as large — looser than WCAG; don't rely on it for bold 11–13 pt labels. Microsoft's doc target is ≥5:1 (windows.md). [HIG Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility)
- **Placeholder, disabled-looking-but-enabled, secondary/"tertiary" labels, timestamps, status-bar text and table header text are the usual failures.** Disabled (inactive) controls are exempt — but then they must really be disabled.
- **1.4.11 Non-text Contrast (AA) ≥ 3:1** against adjacent colors for: focus rings (vs the background *and* vs the control), text-field/checkbox/radio/switch borders when they're the only boundary, selected-row highlight vs unselected (if selection is shown by color), toggle on/off states, meaningful icons (toolbar glyphs!), slider tracks/thumbs, chart lines/bars/segments and their legends, splitters if they're the only drag affordance. [WCAG 2.2](https://www.w3.org/TR/WCAG22/#non-text-contrast)
- **1.4.1 Use of Color (A)**: errors (icon + text, not just red border), status dots (shape/label: ● Online vs ○ Offline), diff views (+/− gutter markers, not only red/green), links in body text (underline), required fields, chart series (patterns/direct labels), "unread" (bold + dot). macOS users can say so explicitly via *Differentiate without color* — but do it always.
- **Dark mode**: re-check every pair; pure #FFF on #000 causes halation for some readers — prefer off-white on very dark gray (still ≥ 7:1). Saturated brand colors often pass on white and fail on dark (or vice versa) → define per-appearance tokens; use system semantic colors (`NSColor.labelColor`, `secondaryLabelColor`, `{ThemeResource TextFillColorSecondaryBrush}`, libadwaita `--window-fg-color`/`.dimmed`). [HIG Color](https://developer.apple.com/design/human-interface-guidelines/color)
- **Translucent materials (vibrancy, Liquid Glass, Mica, Acrylic, CSS `backdrop-filter`)**: contrast is only defined for opaque colors → measure text against the **worst realistic backdrop** (white page *and* black video behind a glass toolbar). Apple: the *regular* glass variant "adjusts the luminosity of background content to maintain legibility"; use it "when components have a significant amount of text" [HIG Materials](https://developer.apple.com/design/human-interface-guidelines/materials). Windows: don't put accent-colored text/links on Acrylic; Mica is a background, keep text on solid layers (windows.md). Always honor Reduce Transparency (§4). macOS/iOS 26.1 added a user "Tinted" Liquid Glass option for more opacity ⚠️ (Six Colors, Nov 2025; not checked on Apple's site).
- **Focus ring color**: accent-colored rings fail when the user's accent is close to your surface color (e.g. graphite accent on gray sidebar) → two-tone ring (accent + 1 px white/black halo) or system ring.
- **Charts & data viz**: ≥3:1 between adjacent series and vs background; don't rely on hue alone; offer a data table view (also gives screen readers the numbers).

## 7. Cognitive load, forms, errors, time

- **Undo everything** (Edit › Undo/Redo, ⌘Z/⇧⌘Z, Ctrl+Z/Ctrl+Y or Ctrl+Shift+Z): name the action ("Undo Move 3 Files"), allow many levels, scroll to and highlight what changed. Prefer **undo over confirmation dialogs** for reversible actions; confirm only destructive irreversible ones (and say exactly what will be lost). [HIG Undo and redo](https://developer.apple.com/design/human-interface-guidelines/undo-and-redo)
- **Autosave + state restoration** = no lost work after crashes, timeouts or accidental quits; reopen windows, selection and scroll position. This is the desktop's biggest cognitive-accessibility win (people with memory or attention impairments get interrupted).
- **3.3.1 / 3.3.3 errors (A/AA)**: say which field and how to fix it in text, next to the field and in a summary for long forms; move focus to the first invalid field on submit (or announce the summary — §3.2). Don't validate-and-scold on every keystroke; validate on blur/submit. [WCAG 2.2](https://www.w3.org/TR/WCAG22/#error-identification)
- **3.3.2 Labels**: visible persistent labels (placeholder ≠ label); units in labels ("Timeout (seconds)").
- **3.3.4 Error prevention (AA)** for legal/financial/data-deleting submissions: reversible, checked, or reviewed before commit.
- **3.3.7 Redundant Entry (A)** — EN 301 549 11.3.3.7 keeps it for software: within one process don't make people re-type what they gave (prefill, "same as billing", remember last export folder/settings). [WCAG 2.2](https://www.w3.org/TR/WCAG22/#redundant-entry)
- **3.3.8 Accessible Authentication (Min, AA)** — EN 11.3.3.8: no memory/transcription/puzzle test without an alternative. Desktop specifics: allow **paste** and password managers in password + OTP fields (don't block Ctrl+V / ⌘V; one-box OTP or a pasteable split); support OS credential APIs (macOS AutoFill/`textContentType` ⚠️, Windows Hello/passkeys, OAuth in the system browser so saved passwords work); "Show password" toggle; device-flow / magic link / passkey sign-in. [WCAG 2.2](https://www.w3.org/TR/WCAG22/#accessible-authentication-minimum)
- **3.2.6 Consistent Help (A)**: void for non-web software in EN 301 549 V4.1.1 (11.3.2.6), but the user need stands: keep **Help** in the same place in every window — the Help menu (macOS: always last menu with search; Windows/GNOME: F1 + primary menu "Help"/"Keyboard Shortcuts"/"About"). [EN 301 549 V4.1.1](https://www.etsi.org/deliver/etsi_en/301500_301599/301549/04.01.01_60/en_301549v040101p.pdf)
- **3.2.1/3.2.2 On Focus / On Input (A)**: focusing or changing a control mustn't open windows, submit, or switch views unexpectedly (e.g. a sidebar list where arrowing triggers heavy loads — use manual activation, §2.2).
- **2.2.1 Timing Adjustable (A)**: any app-imposed limit → off, adjust to ≥10×, or warn and extend with ≥20 s to respond (≥10 times); exceptions: real-time, essential, >20 h. Desktop examples: session lock in banking/enterprise apps, auto-dismissing toasts that contain actions, "undo" snackbars, quiz timers. Toasts with actions should stay until dismissed or follow the OS duration (Windows `UISettings.MessageDuration`, windows.md). [WCAG 2.2](https://www.w3.org/TR/WCAG22/#timing-adjustable)
- **2.2.2 Pause, Stop, Hide (A)**: anything that moves/blinks/scrolls >5 s in parallel with other content (marquees, auto-advancing carousels, animated banners, live tickers) or auto-updates (feeds, dashboards) needs pause/stop/hide. Blinking caret is exempt; **blinking non-caret elements must stop within 5 s**. Flutter exposes `deterministicCursor` for a non-blinking caret. [WCAG 2.2](https://www.w3.org/TR/WCAG22/#pause-stop-hide)
- **Plain language & predictability**: verb-first button labels ("Export PDF", not "OK"); same term for the same thing everywhere (3.2.4 is void for software in EN but still right); short sentences; no double negatives in checkboxes ("Don't not show…"); progressive disclosure for advanced options; empty states that say what to do next. [W3C COGA](https://www.w3.org/TR/coga-usable/)
- **Don't hijack attention**: no modal "rate us"/promo windows on launch, no focus stealing from other apps (only bring a window forward on user action; use notifications/dock bounce/taskbar flash instead).

## 8. Motion & seizures

- **2.3.1 Three Flashes (A)**: ≤ **3 flashes in any 1 s**, or below the general/red flash thresholds: general flash = opposing luminance change ≥ **10 %** with the darker state < **0.80**; red flash: a state with R/(R+G+B) ≥ **0.8** and chromaticity change > 0.2; area limit **25 % of a 10° field ≈ 341×256 px at 1024×768** (WCAG2ICT reuses this for software). Applies to video players, games, loading animations, error "flashing" states, screen-recording overlays. [Understanding 2.3.1](https://www.w3.org/WAI/WCAG22/Understanding/three-flashes-or-below-threshold.html), [WCAG2ICT](https://www.w3.org/TR/wcag2ict-22/)
- **2.3.3 Animation from Interactions (AAA, but cheap — just honor the OS setting)**: motion animation triggered by interaction "can be disabled, unless … essential". Motion = intermediate steps that create movement; **color and opacity changes are not motion; the errata removed "blurring" from that exclusion, so blur-in/out counts as motion**. Named examples: parallax, decorative elements moving in on scroll. [Understanding 2.3.3](https://www.w3.org/WAI/WCAG22/Understanding/animation-from-interactions.html), [WCAG 2.2](https://www.w3.org/TR/WCAG22/#animation-from-interactions)
- **What Reduce Motion should change (don't kill all feedback):**
  - Replace slides, pushes, zooms, flips, parallax, springs with overshoot, 3-D/z-depth and blur transitions with **short cross-fades (~150–200 ms) or instant changes** ⚠️ (duration is a practice, not a spec number). Apple: "avoid large animations, especially those that simulate the third dimension". [Apple accessibilityDisplayShouldReduceMotion](https://developer.apple.com/documentation/appkit/nsworkspace/accessibilitydisplayshouldreducemotion)
  - Keep state feedback: pressed/hover color changes, focus rings, progress indicators (spinner → static/indeterminate bar is fine), selection highlights.
  - Stop autoplaying video/animated images/looping illustrations (Flutter: `autoPlayAnimatedImages`, `autoPlayVideos`); smooth-scroll → instant jump for "scroll to" actions.
  - libadwaita ≥1.9 stock widgets already swap slides for cross-fades under reduced motion (linux.md); WinUI built-ins follow Animation effects ⚠️, **your own Storyboards/Composition animations must check `UISettings.AnimationsEnabled`** (windows.md).
- Electron/web pattern:
  ```css
  @media (prefers-reduced-motion: reduce) {
    *, *::before, *::after { animation-duration: .01ms !important; animation-iteration-count: 1 !important;
      transition-duration: .01ms !important; scroll-behavior: auto !important; }
    .panel-enter { transition: opacity 150ms linear !important; transform: none !important; }
  }
  ```
  JS: `matchMedia('(prefers-reduced-motion: reduce)').addEventListener('change', …)` (WCAG technique SCR40). Also add an in-app "Reduce animations" toggle defaulting to *System* (WCAG technique "user preference control").
- SwiftUI: `@Environment(\.accessibilityReduceMotion) var reduce` → `withAnimation(reduce ? Animation.easeInOut(duration: 0.15) : .spring) { … }` and `.transition(reduce ? AnyTransition.opacity : .slide)` (spell out the type in ternaries so inference works).

## 9. Testing workflow

**Automated checks catch only part of the problems** (missing names, bad ARIA, contrast) — Playwright's own docs say many issues need manual testing. Run tools in CI, then do the manual pass below on every OS you ship. [Playwright a11y testing](https://playwright.dev/docs/accessibility-testing), [MS Learn testing](https://learn.microsoft.com/en-us/windows/apps/design/accessibility/accessibility-testing)

### 9.1 macOS
- **Accessibility Inspector** (Xcode › Open Developer Tool): *Inspection* (hover → label, value, role, actions, parent/child), *Audit* (contrast, missing descriptions, hit regions, clipped text), *Settings* panel to flip display options quickly ⚠️ (panel contents not re-checked).
- **XCUITest**: `try XCUIApplication().performAccessibilityAudit()` — available **macOS 14+**; filter with `for: [.contrast, .elementDetection, .hitRegion, .sufficientElementDescription, .textClipped, .trait]` and an issue handler to ignore known false positives. [Apple](https://developer.apple.com/documentation/xcuiautomation/xcuiapplication/performaccessibilityaudit(for:_:))
- **VoiceOver**: ⌘F5 on/off; VO = ⌃⌥ or Caps Lock; VO-H help menu, VO-K keyboard help, VO-Shift-N read hint, **VO-Fn-⌘-F10 caption panel** (shows what's spoken — good for screenshots/bug reports), **VO-Shift-Fn-F11 screen curtain** (test eyes-free). VO-U rotor, VO-Space activate, VO-Shift-↓/↑ interact in/out, VO-A read all ⚠️ (standard, not re-checked). [Apple VoiceOver general commands](https://support.apple.com/guide/voiceover/general-commands-cpvokys01/mac)
- Keyboard: test with Keyboard navigation **off and on** (⌃F7 / System Settings › Keyboard) and with Full Keyboard Access (⌃F1). Display: Increase Contrast, Reduce Transparency, Reduce Motion, Differentiate Without Color, **Show Borders (27)**, Dark.

### 9.2 Windows
- **Accessibility Insights for Windows**: *Live Inspect* (UIA properties on hover/focus), **FastPass** ("less than five minutes"), *Troubleshooting*. Legacy SDK tools: Inspect, AccEvent (events), AccScope (Narrator view), AccChecker, UIA Verify. [MS Learn](https://learn.microsoft.com/en-us/windows/apps/design/accessibility/accessibility-testing)
- **Narrator**: Win+Ctrl+Enter; Caps Lock+arrows to read; Caps Lock+Enter invoke; Caps Lock+F1 command list; Caps Lock+F description; **Ctrl+Caps Lock+F12 developer mode** (masks everything not exposed to UIA — instantly shows custom-drawn UI that's invisible to AT). Turn the monitor off and finish the main task. [MS Learn](https://learn.microsoft.com/en-us/windows/apps/design/accessibility/accessibility-testing)
- **NVDA** (free, widely used): Ctrl+Alt+N start; NVDA key = Insert (or Caps Lock); NVDA+Tab report focus, NVDA+T window title, NVDA+F7 elements list, NVDA+S speech mode, NVDA+Q quit; Tools › Speech Viewer to see output ⚠️ (menu path). [NVDA User Guide](https://download.nvaccess.org/documentation/userGuide.html)
- Contrast themes: Left Alt+Left Shift+PrtScn, test **Aquatic, Desert, Dusk, Night sky** live; Text size 225 %; Animation effects off; Transparency effects off; 200 % display scaling.

### 9.3 Linux
- **Orca**: Super+Alt+S toggles (GNOME); Orca modifier = Insert (desktop layout) or Caps Lock (laptop layout); Orca+Space preferences; Orca+H learn mode, Esc exits. [Orca help](https://help.gnome.org/users/orca/stable/commands_controlling_orca.html)
- **Accerciser** (AT-SPI tree, properties, event monitor; 3.48 current in distros) and **GTK Inspector** (Ctrl+Shift+D or `GTK_DEBUG=interactive`) → Accessibility tab. [Arch package](https://archlinux.org/packages/extra/any/accerciser/), linux.md
- GNOME Settings › Accessibility: High Contrast, Large Text, reduced animations; also test under KDE Plasma if you ship Qt.

### 9.4 Electron / Tauri / web views
```ts
// npm i -D @playwright/test @axe-core/playwright
import { _electron as electron, test, expect } from '@playwright/test';
import AxeBuilder from '@axe-core/playwright';
test('main window has no axe violations', async () => {
  const app = await electron.launch({ args: ['.'] });           // experimental; Electron v21+
  const page = await app.firstWindow();
  await page.emulateMedia({ forcedColors: 'active', reducedMotion: 'reduce' }); // also run without
  const r = await new AxeBuilder({ page }).withTags(['wcag2a','wcag2aa','wcag21a','wcag21aa','wcag22aa']).analyze();
  expect(r.violations).toEqual([]);
  await app.close();
});
```
- Sources: [Playwright Electron](https://playwright.dev/docs/api/class-electron), [Playwright + axe](https://playwright.dev/docs/accessibility-testing). ⚠️ `wcag22aa` tag and `emulateMedia({forcedColors})` from axe/Playwright knowledge, not on the fetched pages; AxeBuilder on an Electron `Page` not verified.
- **DevTools**: Elements › Accessibility pane + "Show accessibility tree" (full-page tree, computed name/role); **Rendering tab emulates** `prefers-color-scheme`, `forced-colors`, `prefers-contrast`, `prefers-reduced-motion`, `prefers-reduced-transparency`, vision deficiencies. [Chrome DevTools a11y reference](https://developer.chrome.com/docs/devtools/accessibility/reference)
- Chromium only builds the native tree when AT is running → set `app.setAccessibilitySupportEnabled(true)` in test builds when inspecting with Accessibility Insights / Accessibility Inspector. [Electron](https://www.electronjs.org/docs/latest/tutorial/accessibility)
- Tauri: test each OS's engine separately — WebView2 (Chromium) on Windows, **WKWebView on macOS (no `prefers-reduced-transparency`)**, WebKitGTK on Linux. [MDN BCD](https://github.com/mdn/browser-compat-data/blob/main/css/at-rules/media.json)

### 9.5 The 10-minute manual check (ask a human to run it; ~1 min each)
1. **Mouse away.** From launch, do the core task with keyboard only: Tab/Shift+Tab, arrows inside lists/toolbars, F6 between panes, Esc closes popovers, Shift+F10 opens context menus. Focus is always visible and never lost/trapped. (macOS: repeat with Keyboard navigation on.)
2. **Menus & shortcuts.** Every toolbar/context action also exists in the menu bar or app menu, with its shortcut shown; no single-letter shortcut fires while typing in a text field.
3. **Screen reader, 2 min.** VoiceOver ⌘F5 / Narrator Win+Ctrl+Enter / Orca Super+Alt+S. Tab across the toolbar and one form: each control speaks a sensible name + role + state (no "button", "unlabeled", "image", file names). Window title is spoken and meaningful.
4. **Announcements.** Trigger a save/export and a validation error: both are spoken without focus jumping; the toast doesn't vanish before it's read.
5. **High contrast.** macOS Increase Contrast + Reduce Transparency (+ Show Borders on 27); Windows Left Alt+Left Shift+PrtScn (check Aquatic and Desert); GNOME High Contrast. All text, icons, borders, selection and focus ring visible; no invisible SVG icons.
6. **Big text.** Windows Text size 225 % or app zoom ⌘/Ctrl + ×3 (≥200 %): no clipped, overlapping or truncated-without-tooltip text; dialogs grow or scroll.
7. **Small window.** At 200 % display scaling shrink the window to its minimum (aim for 640 physical px = 320 pt/epx): every function still reachable (overflow menus, collapsible sidebar), forms scroll vertically only.
8. **Motion.** Reduce Motion / Animation effects off: view switches and sidebars fade or cut, nothing slides, zooms or parallaxes; nothing flashes.
9. **Pointer.** Hover a custom tooltip: you can move onto it and Esc dismisses it; tab-close ×, splitters and icon buttons are easy to hit (≥24 px); every drag (reorder, move, resize) has a menu or keyboard alternative.
10. **Forms & safety.** Paste works in password/OTP fields; errors are described in text next to the field; Undo reverses a delete; color is never the only signal (check in grayscale).

## 10. Desktop accessibility anti-patterns (seen constantly in generated apps)

- Custom-drawn list/tree/table/tabs/menus (div soup, Canvas, Skia) with mouse handlers only → no Tab stop, no arrows, nothing in the accessibility tree. Use toolkit controls or implement the APG pattern *and* the AT node.
- `outline: none` / `UseSystemFocusVisuals="False"` / focus ring hidden "because it looks ugly"; or a focus ring only via `box-shadow` (disappears in forced colors).
- Every button a Tab stop on macOS while lists aren't keyboard-navigable (backwards: on Mac, lists/fields first, buttons via Full Keyboard Access).
- Hover-only affordances: row actions, resize handles, tooltips carrying essential info, toolbars that appear on hover.
- Icon-only toolbar with no accessible names (and tooltips used as the "label"); names like "btn-1", "icon", "Save button".
- Toasts that auto-dismiss in 3 s and are never announced; spinners with no "Loading…/Done" announcement; errors shown only as red borders.
- Hard-coded hex colors (invisible in Windows contrast themes / dark mode); gray placeholder-like secondary text < 4.5:1; light text on glass/Mica.
- Fixed-size dialogs and windows that clip at 200 % text or 225 % Windows text size; min window size wider than a half-screen.
- Animations that ignore Reduce Motion / Animation effects; blur transitions (count as motion); parallax hero headers in "about" screens.
- Single-letter shortcuts always active (2.1.4); shortcuts that override VoiceOver/NVDA/Orca keys or OS shortcuts; F6 not implemented.
- Custom title bars that drop the window title (AT reads nothing meaningful) and hand-drawn caption buttons without names.
- Electron apps that remove the default menu (losing Zoom In/Out, Undo, Copy/Paste roles) and replace it with nothing.
- Drag-only reordering/moving; down-event activation; tiny 12–16 px close/disclosure targets packed edge to edge.
- Blocking paste in password/OTP fields; CAPTCHAs/puzzles in desktop sign-in; embedded login web views that bypass password managers.
