# macOS app design

Read this for any Mac app: SwiftUI, AppKit, Mac Catalyst, or a cross-platform shell (Electron, Tauri, Flutter, Qt) running on macOS. Covers macOS 26 Tahoe (Liquid Glass) and macOS 27 (WWDC26). Every rule cites its source inline; ⚠️ marks claims that couldn't be fully verified (collected at the end). Researched November 2026 — platform details change, so re-check anything version-specific.

## 0. TL;DR — the 15 rules that matter most
1. **Menu bar is the app's table of contents.** App · File · Edit · Format · View · *custom* · Window · Help, in that order; *every* command lives there (toolbar/context/Dock items too) with standard shortcuts; disable, don't hide (§3).
2. **Never repurpose standard shortcuts** (⌘N/O/S/W/Q/Z/C/V/F/,/?…); custom ones use ⌘ first, avoid ⌃ (§3).
3. **"Settings…" ⌘, in the App menu** opens a separate pane-toolbar window; changes apply instantly; no gear in the main toolbar (§5).
4. **System windows only**: real traffic lights, unified title/toolbar, resizable with a sane min size, system full screen; never custom frames (§2).
5. **Quit instantly, relaunch exactly where people left off** (windows, selection, scroll, panes) (§2, WWDC26 289).
6. **Sidebar → (list) → detail split view + trailing inspector** is the default Mac layout; ≤2 sidebar levels; panes hideable with toolbar button *and* menu item (§4).
7. **Toolbar**: SF Symbols without borders, ≤3 groups, one prominent primary action trailing, search trailing; customizable for pro apps; nothing toolbar-only (§4).
8. **Mac density**: 13 pt body (no Dynamic Type), regular controls 24 pt tall (mini 16/small 20/large 28/XL 36 on Tahoe), never hard-code heights; XL only for the one hero action (§6–7).
9. **Respect the user's system choices**: accent color (yours only under Multicolor), Light/Dark/Auto (no in-app theme switch), Reduce Transparency, Increase Contrast, sidebar icon size, macOS 27 glass slider & Show Borders (§7).
10. **Keyboard-complete**: logical Tab order, focus rings, Return = default button, Esc/⌘. = cancel, arrow keys + type-select in lists, Delete deletes (§8).
11. **Undo everything, alert rarely**: unlimited named undo instead of "Are you sure?"; alerts only for un-undoable destructive actions, verb buttons, "Cancel" never default (§5–6).
12. **Drag and drop in, out, and to Finder**, copy/paste, Services, Share, Quick Look — use system text views, open/save/print panels (§6).
13. **Liquid Glass only on floating controls**, never on content; no custom backgrounds behind system bars; remove old sidebar `NSVisualEffectView`s; icons in menus only with purpose (macOS 27 hides them by default) (§1).
14. **Permissions at the moment of use** with specific purpose strings; for Accessibility/Screen Recording/Full Disk Access explain, deep-link to System Settings, detect the grant (§5).
15. **Touch is now a Mac input (MacBook Pro, Oct 2026)**: keep density, make hover-only controls reachable by tap/context menu, use gesture recognizers not `mouseDown` loops (§6).

## 1. Current state: macOS 26 Tahoe, Liquid Glass, WWDC26 / macOS 27
**Timeline.** macOS 26 **Tahoe** (WWDC25, June 2025; shipped Sept 2025) introduced **Liquid Glass**: toolbars and sidebars become floating glass, controls redesigned, menus full of icons, new app icon system (Icon Composer). **macOS 27 "Golden Gate"** — announced at WWDC26 keynote **June 8, 2026**, released **Sept 14, 2026** (https://www.apple.com/newsroom/2026/09/major-updates-for-apples-software-platforms-are-now-available/; release notes title "macOS 27 Golden Gate Release Notes" https://developer.apple.com/documentation/macos-release-notes/macos-27-release-notes). Xcode 27 rebuilds pick up the refined design automatically ("once your app is recompiled with Xcode 27, it will automatically begin to use the new design with Liquid Glass" — Platforms State of the Union https://developer.apple.com/videos/play/wwdc2026/102/). macOS 26 was the **last Intel release**; Mac App Store accepts Apple-silicon-only binaries; macOS 27 Settings lists Intel apps that will stop working in **macOS 28** (release notes). Design resources (https://developer.apple.com/design/whats-new/): **SF Symbols 8** and **Icon Composer 2** (June 8, 2026), macOS 27 UI Kits for Figma/Sketch.
**First touchscreen Mac:** "MacBook Pro with PROLED XDR Display", 14"/16", M5 Pro/Max, announced **Oct 28, 2026**, ships Nov 6, 2026: "macOS automatically translates touches into clicks"; "Updated system gesture APIs also enable developers to create intuitive experiences designed specifically for Touch" (https://www.apple.com/newsroom/2026/10/apple-unveils-groundbreaking-macbook-pro-with-proled-xdr-display/). HIG touch guidance added the same day (see §6).

**What macOS 26 Tahoe changed (WWDC25 "Build an AppKit app with the new design", https://developer.apple.com/videos/play/wwdc2025/310/):**
- Toolbar items sit on glass; AppKit **auto-groups** adjacent buttons onto one glass capsule; segmented controls, pop-ups and search get their own. Override with `NSToolbarItemGroup` / spacers. Non-interactive items (titles, status text) must **not** sit on glass: `NSToolbarItem.isBordered = false`. Tint a key action: `NSToolbarItem.style = .prominent` (+ `backgroundTintColor`); badges: `NSItemBadge`.
- Sidebars = floating glass pane; inspectors = edge-to-edge glass. Get both free from `NSSplitViewController` with sidebar/inspector split items. **Remove old `NSVisualEffectView` sidebar materials** — they block the glass. Let content run under the sidebar: `automaticallyAdjustsSafeAreaInsets = true` on the *content* item; mirror/blur hero art under it with `NSBackgroundExtensionView` (SwiftUI `.backgroundExtensionEffect()`).
- **Concentric corners**: window radius grew and varied by window style in 26 (toolbar windows rounder); keep content out of corners with `NSView.LayoutRegion` (corner adaptation).
- Scroll edge effect (soft = fade/blur; **hard = more opaque, "mostly used on macOS"** — https://developer.apple.com/videos/play/wwdc2025/356/) under toolbars/titlebar accessories; `NSSplitViewItemAccessoryViewController` for per-pane floating bars.
- Controls: new **extra large** size (for the one action people open the app to do); **mini/small/medium are slightly taller** than in macOS 15 → never hard-code control heights, use Auto Layout. Dense inspectors can opt back: `NSView.prefersCompactControlSizeMetrics = true` (SwiftUI: `.controlSize(.small)` etc.). Mini–medium stay rounded-rects (density); large/XL become capsules. `borderShape` overrides; `.glass` bezel style; `tintProminence` (`.primary/.secondary/.none`) — destructive buttons use red at secondary prominence so they don't outshout the default button. Sliders: `neutralValue` anchors the fill.
- Glass for custom UI only on the top functional layer (floating controls), never on content: `NSGlassEffectView` (set `contentView`, don't put it behind as a sibling) inside `NSGlassEffectContainerView` for nearby shapes (shared sampling, morphing, performance). SwiftUI: `.glassEffect()`, `GlassEffectContainer`.
- Glass recedes when the window loses key status (WWDC25 Meet Liquid Glass, https://developer.apple.com/videos/play/wwdc2025/219/).

**What macOS 27 (WWDC26) changed** — "Modernize your AppKit app" https://developer.apple.com/videos/play/wwdc2026/289/ + SOTU 102 + "What's new in SwiftUI" https://developer.apple.com/videos/play/wwdc2026/269/:
- Glass tuned to diffuse busy content better; **new user slider "ultra clear ↔ fully tinted"** in Settings — your glass must look right at both ends (automatic for system glass).
- **Every window now has the same, tighter corner radius** (reverses Tahoe's per-style radii).
- **Sidebars extend to the window edges**; sidebar icons **regain color** (app accent color); selected sidebar row uses **semibold** text. Bordered toolbar items over the sidebar are glass too.
- Automatic scroll edge effect resolves to **hard edge** when free-floating text (window title) is present → a "uniform toolbar" band keeps titles legible.
- **Menus: icons mostly removed** after the Tahoe backlash. Release notes: "menu bar and context menus present a reduced set of menu item images, similar to the behavior prior to macOS 26.0. By default, `NSMenu` hides all menu item symbol images" (apps linked on 26+; on the 27 SDK non-symbol images are hidden too). System keeps defaults for a few common items (Settings, Share, Print). Keep one deliberately: AppKit `NSMenuItem.preferredImageVisibility`, SwiftUI `.labelStyle(.titleAndIcon)` "such as when the menu item represents an object or a concept rather than an action". HIG Menus (June 8, 2026): "Use menu item icons sparingly and with purpose."
- Also in 27: AppKit `NSRefreshController` (pull-to-refresh in `NSScrollView`), `NSScrollView` properties to set touches-needed-to-scroll, `NSToolbarItemGroup.role`, `NSApplication.presentationOptions` `.disableScreenCornerInteractions` (release notes).
- macOS 27 supports the **"Show borders" (button shapes)** accessibility setting like iOS → custom controls must draw a visible border when it's on (iOS SwiftUI env is `accessibilityShowButtonShapes`; not present in the macOS 26 SDK — expect it in the 27 SDK ⚠️).
- Interactive glass "bounce" on click (SwiftUI `.glassEffect(.regular.interactive())`; use only on controls).
- AppKit: `NSViewCornerConfiguration` + `.containerConcentric` radius (with a minimum), control events (`NSControlEvents`, no subclassing), `NSTextSelectionManager`, status-item `expandedInterfaceSession`, **`preventsApplicationTerminationWhenModal = false`** (existing API since 10.6, newly emphasized) for sheets that needn't block quit; gesture recognizers instead of `mouseDown` tracking loops; `autorecalculatesKeyViewLoop`.
- SwiftUI: `ToolbarOverflowMenu` container (send low-priority actions to the overflow menu), `topBarPinnedTrailing` placement, `toolbarMinimizeBehavior`, `appearsActive` env value to dim custom chrome in inactive windows, interactive glass on Mac.

**Apple's design principles (HIG, reintroduced June 8, 2026 — https://developer.apple.com/design/human-interface-guidelines/design-principles; WWDC26 "Principles of great design" https://developer.apple.com/videos/play/wwdc2026/250/):** Purpose · Agency · Responsibility · Familiarity · Flexibility · Simplicity · Craft · Delight. Mac-relevant lines: "Stay out of the way… get them directly to the task"; "When a guided flow is necessary, make it easy to skip or escape"; "Help people recover from mistakes" (undo over confirmation); "use system patterns to display alerts and offer choices"; "Approach every platform with intention… Give each platform you support the same level of care"; "Simplicity isn't minimalism"; "Don't mistake delight for decoration."

**HIG "Designing for macOS"** (https://developer.apple.com/design/human-interface-guidelines/designing-for-macos, updated Oct 28, 2026): large high-res displays, desk ergonomics, keyboard + pointer primary, sessions "from a few minutes… to several hours of deep concentration", many apps open at once. Best practices: more content in **fewer nested levels with less modality**; let people resize/hide/move windows + support full screen; **menu bar holds all commands**; handle keyboard shortcuts for keyboard-only work; support high-precision pointer edits; support standard trackpad **and touch** gestures ("larger tap targets and controls that expand on touch… while keeping control size and density the same"); allow personalization (customizable toolbars, window configuration, colors, fonts).

## 2. Windows
Sources: HIG Windows https://developer.apple.com/design/human-interface-guidelines/windows, Panels …/panels, Going full screen …/going-full-screen, Layout …/layout.
- **Kinds.** *Primary* window (main navigation + content) vs *auxiliary* window (one task, no navigation, a close button). On Mac also: **document windows** (one per file, title = filename, edited dot, proxy icon), **panels** (`NSPanel`, floating utility: Fonts, Colors, Inspector — key only when a text field/title bar is clicked), **HUD panels** (dark translucent, only in media apps / full screen; few controls), **About window**, **Settings window**.
- **States**: *main* (front window of the app), *key* (receives input; colored traffic lights), *inactive* (gray controls, no material/vibrancy, looks farther away). Custom chrome must replicate all three — so don't build custom chrome. In SwiftUI read `@Environment(\.appearsActive)` to dim custom controls in inactive windows.
- **Never build custom window frames or traffic lights.** "Avoid making custom window frames or controls, and don't try to replicate the system-provided appearance… can make your app feel broken." Call it a "window" in UI copy (never "scene").
- **Open new windows deliberately**: don't open windows by default; offer "Open in New Window" in the File menu / context menu (`openWindow`/`OpenWindowAction`). Mail-style compose window is the canonical good case.
- **Sizing.** Windows must adapt fluidly to any size; set sensible **minimum** sizes so layouts never overlap and split-view dividers never vanish (HIG Split views). Pick a default size that suits content and fits the smallest common Mac screen — 13" MacBook Air default "looks like" 1470×956 pt ⚠️ (minus menu bar 24 pt + Dock); a practical floor is ~800×500 for a three-pane app ⚠️ (practitioner heuristic). SwiftUI: `.defaultSize(width:height:)`, `.frame(minWidth:minHeight:)`, `.windowResizability(.contentMinSize)`; AppKit: `contentMinSize`, `setFrameAutosaveName`.
- **Zoom** (green button option-click / Window › Zoom) = toggle "best fit for content" ↔ user size; never use it for full screen.
- **Full screen**: use the system implementation (`toggleFullScreen(_:)`; SwiftUI windows get it free) — it handles the notch/camera housing. Let people choose when to enter (green button, View › Enter Full Screen, ⌃⌘F); never auto-exit; don't programmatically resize; keep essential controls reachable; Dock stays reachable (except games); may auto-hide toolbars, restore on pointer-to-top. Don't put content behind the camera housing (`NSPrefersDisplaySafeAreaCompatibilityMode`).
- **Tabs**: support native window tabbing for document/browser-like apps (system adds Window › Merge All Windows, Show Tab Bar, ⌃⇥). AppKit `NSWindow.tabbingMode`/`tabbingIdentifier`; SwiftUI `WindowGroup` participates automatically.
- **Bottom bars**: avoid critical info/actions at the **bottom** of windows or sidebars (people drag windows partly off-screen); a small status bar is OK (Finder item count). More info → inspector.
- **Title + toolbar**: give every window a useful title, **never the app name**, aim **<15 characters**; may leave empty when content self-titles (Notes) — https://developer.apple.com/design/human-interface-guidelines/toolbars. Unified title/toolbar is the modern default: SwiftUI `.windowToolbarStyle(.unified)` / `.unifiedCompact` / `.expanded`; AppKit `NSWindow.toolbarStyle`. Subtitles: `.navigationSubtitle` (e.g. "12 messages"). Hidden title bar for utility/media windows: `.windowStyle(.hiddenTitleBar)` (traffic lights stay).
- **State restoration** (WWDC26 289): "a great Mac app seamlessly quits and quickly restores… comes back as if it was never quit." Restore open windows, frames, which was frontmost/minimized/full screen, selection, scroll position, sidebar width, inspector visibility. Don't serialize document data — only UI state. AppKit: `isRestorable`, `restorationClass`, `encodeRestorableState`/`restoreState`, `invalidateRestorableState()`, autosave names for non-document windows; always call the restore completion handler. SwiftUI: `WindowGroup` restores automatically; persist per-window UI with `@SceneStorage`, app-wide with `@AppStorage`; opt specific windows out with `.restorationBehavior(.disabled)` (macOS 15+).
- **Quit without pushback**: only block quit for unsaved data; set `preventsApplicationTerminationWhenModal = false` on non-critical sheets (WWDC26 289). Closing the last window: document/multi-window apps keep running; single-window utilities may quit (SwiftUI `Window` scene quits when closed ✓; AppKit `applicationShouldTerminateAfterLastWindowClosed`).
- **Spacing/margins**: modern HIG gives no fixed Mac margin numbers; use system layout margins/safe areas (`NSView.LayoutRegion`, SwiftUI default `.padding()` ≈ 16 pt ⚠️) and Interface Builder/SwiftUI default spacing (8 pt sibling, 20 pt window edge was the classic AppKit standard ⚠️ legacy HIG). Bezelled elements: ~12 pt padding; non-bezelled: ~24 pt (HIG Accessibility, https://developer.apple.com/design/human-interface-guidelines/accessibility). Keep content out of the larger window corners.

## 3. Menu bar, Dock menus, context menus, keyboard shortcuts
Source unless noted: HIG The menu bar https://developer.apple.com/design/human-interface-guidelines/the-menu-bar (fetched 2026-11-02).

**Menu order (fixed):** Apple menu (system, can't touch) · **AppName** (bold, short name) · File · Edit · Format · View · *app-specific menus* · Window · Help · … menu bar extras (trailing). Drop File only if the app handles no files; drop Format if no rich text. **Always ship View and Window menus**, even for one-window apps (View may hold only Enter/Exit Full Screen; Window must hold Minimize + Zoom for Full Keyboard Access users).

**Rules**
- Every command lives in the menu bar — including ones also in toolbars, context menus, or Dock menus. "Excluding commands from the menu bar — even infrequently used or advanced commands — risks making them difficult for everyone to find." Menu items are also what Full Keyboard Access and shortcut discovery use.
- Never hide menu-bar items when not applicable — **disable (dim)** them. A menu whose items are all disabled still opens. (Opposite rule for context menus: hide irrelevant items; only Cut/Copy/Paste may appear dimmed — https://developer.apple.com/design/human-interface-guidelines/context-menus.)
- Menu titles: one word preferred; title-style capitalization; drop articles ("View Settings", not "View the Settings") — https://developer.apple.com/design/human-interface-guidelines/menus.
- **Ellipsis (…, the single character U+2026)** only when the item needs more input before completing (Open…, Print…, Export As…, Rename…, Settings…). No ellipsis for items that act immediately or just show a window/panel that needs no input (About, Show Fonts).
- Show/hide items reflect state: "Show Toolbar" ↔ "Hide Toolbar", "Show Sidebar" ↔ "Hide Sidebar". Checkmarks for attributes in effect (Format › Font › Bold).
- Undo/Redo name the action: "Undo Paste and Match Style", "Undo Typing".
- Submenus: one level, roughly ≤5 items, title = the repeated term ("Sort By ▸ Date / Name / Size"). Don't indent items instead of using a submenu.
- Menu-item icons (macOS 26 put icons on nearly every item; macOS 27 hides symbol images by default — see §1): "Use menu item icons sparingly and with purpose" — for common actions (use the system's standard symbols for Copy/Share/Delete…), key features, file locations, devices, visual concepts (rotate/flip), user content. **Icons for all items in a group, or none.** Don't invent an icon if none clearly fits. (HIG Menus, change log "June 8, 2026 — Updated guidance for menu item icons" — reversed after the Tahoe icon backlash, e.g. Prokopov https://tonsky.me/blog/tahoe-icons/ "Fifty Shades of 'New'".) Practical rule for 27: icons only for objects/places/devices and a handful of signature actions; zero icons is a fine default.
- Dynamic (alternate) items: reveal with **one** modifier only (Option is typical: Close→Close All, Minimize→Minimize All, Quit→Quit and Keep Windows). Never the only path to a task. Menu bar only, not context/Dock menus. AppKit `NSMenuItem.isAlternate`.
- Custom shortcuts appear in menus; **don't show shortcuts in context menus**.

**App menu (in order):** About AppName (alone in first group; name ≤16 chars, no version number in the title) · Settings… (⌘,) · app-level config items · Services · Hide AppName (⌘H) · Hide Others (⌥⌘H) · Show All · Quit AppName (⌘Q; ⌥ → Quit and Keep Windows). Use the term **"Settings…"** (renamed from "Preferences…" in macOS 13 Ventura; ⚠️ the "renamed in Ventura" date is from memory, the HIG now only says Settings…). Document-specific settings go in **File**, not Settings.

**File:** New *Item* (name the thing: "New Event") ⌘N · Open… ⌘O · Open Recent ▸ (most-recent first, display names not paths, "Clear Menu") · Close ⌘W (⌥ → Close All; tabbed window: Close Tab, add Close Window ⇧⌘W) · Save ⌘S · Duplicate ⇧⌘S (⌥ → Save As…; prefer Duplicate over Save As/Export/Save To) · Rename… · Move To… · Export As… · Revert To ▸ · Page Setup… ⇧⌘P · Print… ⌘P. Autosave so people rarely need Save.
**Edit:** Undo ⌘Z · Redo ⇧⌘Z · Cut ⌘X · Copy ⌘C · Paste ⌘V · Paste and Match Style ⌥⇧⌘V · Delete (call it Delete, never Erase/Clear) · Select All ⌘A · Find ▸ (Find… ⌘F, Find and Replace… ⌥⌘F ⚠️, Find Next ⌘G, Find Previous ⇧⌘G, Use Selection for Find ⌘E, Jump to Selection ⌘J) · Spelling and Grammar ▸ · Substitutions ▸ · Transformations ▸ · Speech ▸. The system appends AutoFill/Start Dictation/Emoji & Symbols itself — don't add them. Find for *objects/files* (not text) may belong in File.
**Format:** Font ▸ (Show Fonts ⌘T, Bold ⌘B, Italic ⌘I, Underline ⌘U, Bigger ⌘+, Smaller ⌘-, Show Colors ⇧⌘C, Copy Style ⌥⌘C, Paste Style ⌥⌘V) · Text ▸ (Align Left ⌘{, Center ⌘|, Justify, Align Right ⌘}, Writing Direction, Show Ruler, Copy/Paste Ruler).
**View:** Show/Hide Tab Bar · Show All Tabs · Show/Hide Toolbar (⌥⌘T) · Customize Toolbar… · Show/Hide Sidebar (⌃⌘S is the system default in SwiftUI/AppKit ⚠️) · Enter/Exit Full Screen (⌃⌘F; system also binds fn-F / 🌐F). View is for *appearance of windows*, never for window navigation.
**App-specific menus** sit between View and Window, ordered general→specific, mirroring the app's object hierarchy (Mail: Mailbox › Message › Format; Safari: History, Bookmarks).
**Window:** Minimize ⌘M (⌥ → Minimize All) · Zoom (⌥ → Zoom All; never use Zoom for full screen) · Show Previous/Next Tab (⌃⇧⇥ / ⌃⇥) · Move Tab to New Window · Merge All Windows · Bring All to Front (⌥ → Arrange in Front) · list of open windows (alphabetical; no panels). Optional show/hide items for your panels (not Fonts/Colors — those are in Format).
**Help:** search field appears automatically (searches menu items too — a big reason every command must be in a menu) · AppName Help (Help Book / `NSHelpManager`, ⌘?) · separator · few extras (release notes, support). Keep it short.

**Menu bar extras (status items)** — menu bar is **24 pt tall**. Use a template (black+clear) image or SF Symbol so the system can tint it. Click shows a **menu, not a popover**, unless the UI is too complex for a menu. Let people choose whether it appears (setting; can offer at setup). Don't depend on it being visible — the system hides extras when space is tight (notch!); also offer a Dock menu. SwiftUI `MenuBarExtra` (`.menuBarExtraStyle(.menu)` default vs `.window`); AppKit `NSStatusBar.system.statusItem(withLength:)`.
**Dock menu** — https://developer.apple.com/design/human-interface-guidelines/dock-menus: Control/secondary-click the Dock icon. Add a few high-value items useful when the app isn't frontmost (Mail: Get New Mail, New Message) + open windows; everything must also exist elsewhere. AppKit `applicationDockMenu(_:)` (SwiftUI has no native API; use `NSApplicationDelegateAdaptor`).
**Context menus** — https://developer.apple.com/design/human-interface-guidelines/context-menus: Control-click / secondary click. Short, ≤ ~3 separator groups, most-used items nearest the pointer, one submenu level max, no title (unless it clarifies, e.g. "3 Messages"), no shortcuts shown, consistent everywhere (if rows have one, all rows have one), and every item also in the menu bar. On Mac, prefer a context menu over opening a panel/inspector for frequent actions.

**Standard shortcuts you must not repurpose** (HIG Keyboards https://developer.apple.com/design/human-interface-guidelines/keyboards — full table there):

| ⌘Q / ⌘H / ⌥⌘H | Quit / Hide app / Hide others | ⌘M / ⌥⌘M | Minimize / Minimize all |

Avoid ⌥/⇧ + non-letter keys (not on every layout); the system localizes and mirrors shortcuts for RTL. Expected modifiers: ⌘-drag moves as group, ⇧-resize keeps aspect ratio, arrow keys nudge by the smallest unit.

## 4. Toolbars, sidebars, split views, inspectors
**Toolbars** (HIG https://developer.apple.com/design/human-interface-guidelines/toolbars, updated Dec 16, 2025):
- Lives in the window frame, unified with the title bar. Mac toolbar items have **no bezel**; use **SF Symbols without borders** (no outlined-circle symbols — the glass group is the container; hover/pressed states come free).
- Three zones: **leading** = sidebar toggle, back/forward, title, optional document menu (Duplicate/Rename/Move/Export) — not customizable · **center** = common controls; customizable; collapses into the system overflow (») menu as the window narrows · **trailing** = always-visible important items, inspector toggle, **search field**, More menu, and the single **primary action** (`.prominent`, tinted with accent; only one).
- **≤ 3 groups.** Group by function/frequency; separate text-labeled buttons with fixed space (two text buttons side by side read as one). Don't add your own overflow menu; avoid layouts that overflow at default size.
- **Every toolbar item must also be a menu command** (toolbars can be hidden/customized). Not every menu item deserves a toolbar slot.
- Allow customization (View › Customize Toolbar…) for long-session/pro apps: SwiftUI `.toolbar(id:)` with `ToolbarItem(id:)`; AppKit `NSToolbar.allowsUserCustomization`, `autosavesConfiguration`.
- Don't paint toolbar backgrounds or tint items in the content's color; let content + scroll edge effect do it. Custom shapes must be concentric with the bar.
- Window title: useful, not the app name, <15 chars.
- macOS 27 SwiftUI: `ToolbarOverflowMenu { … }` for rarely used actions, `.topBarPinnedTrailing` to pin share/primary to the trailing edge (https://developer.apple.com/videos/play/wwdc2026/269/).
- Modal editing states may swap in a contextual toolbar; restore the standard one on exit.

**Search placement** (WWDC26 "Design intuitive search experiences" https://developer.apple.com/videos/play/wwdc2026/292/; HIG Searching https://developer.apple.com/design/human-interface-guidelines/searching): split-view apps searching across columns (Mail) → **trailing toolbar**; it scales or collapses to a button as space shrinks, and expands when activated. Filtering what's in the sidebar → **search field in the sidebar** (top). Recent searches as a menu. Show the current scope (placeholder "Search Inbox", scope bar/tokens). ⌥⌘F focuses search; ⌘F = find in document. Index content for Spotlight (Core Spotlight), provide Quick Look previews for custom file types. SwiftUI: `.searchable(text:placement: .toolbar | .sidebar)`, `.searchSuggestions`, `.searchScopes`.

**Sidebars** (https://developer.apple.com/design/human-interface-guidelines/sidebars, updated June 8, 2026):
- Leading-edge navigation between top-level areas/collections (source list). In 26 it floats as glass; in 27 extends to window edges. Let rich content extend beneath (`.backgroundExtensionEffect()`).
- **≤ 2 levels** of hierarchy (disclosure groups with succinct section titles); deeper → add a content-list column (three-pane).
- Icons: SF Symbols (custom → custom symbol, not bitmap). Default tint = **app accent color, and must follow the user's system accent color** when they change it; fixed colors only sparingly with meaning (Mail VIP yellow).
- Row/text/icon size follows the user's **Sidebar icon size** (small/medium/large, System Settings › Appearance) — don't hard-code row heights.
- Collapsible: toolbar button + View › Show/Hide Sidebar (⌃⌘S ⚠️); auto-collapse when the window gets narrow; **don't hide by default**. Nothing critical at the bottom. Let people customize contents/order when possible.
- AppKit: `NSSplitViewItem(sidebarWithViewController:)` + `NSOutlineView` with `.sourceList` style (⚠️ in 26 `style = .automatic` resolves to source list inside sidebar items). SwiftUI: `List(selection:)` inside `NavigationSplitView` sidebar column (`.listStyle(.sidebar)` automatic).

**Split views & three-pane layout** (https://developer.apple.com/design/human-interface-guidelines/split-views): sidebar | content list | detail (Mail, Notes, Finder column-ish). Persistently highlight the selection in every pane leading to the detail. Allow drag and drop between panes. Set min/max pane widths so dividers never disappear; **thin divider (1 pt)** preferred. Let people hide panes, with ≥2 ways to bring them back (toolbar button + menu item with shortcut). Save divider positions (`NSSplitView.autosaveName`; SwiftUI `.navigationSplitViewColumnWidth(min:ideal:max:)`).

**Inspectors**: trailing pane showing properties of the current selection, updates live as selection changes (vs. an *Info window*, which is fixed to one item → regular window; HIG Panels). In 26+ an edge-to-edge glass pane. Toggle: trailing toolbar button + View/Window menu "Show Inspector" (⌥⌘I). Mini/small controls OK here (density; `prefersCompactControlSizeMetrics`). SwiftUI `.inspector(isPresented:)` + `.inspectorColumnWidth(min:ideal:max:)`; AppKit `NSSplitViewItem(inspectorWithViewController:)`. Bottom status bar only for tiny contextual info.

## 5. Settings, modality (sheets/alerts/popovers/panels), onboarding, launch, privacy prompts
**Settings window** (https://developer.apple.com/design/human-interface-guidelines/settings):
- Opened only from **AppName › Settings… (⌘,)**. **No settings/gear button in the main toolbar.** Document-level options → File menu.
- Toolbar of **pane buttons** (icon + short label: General, Accounts, Advanced…), **not customizable**, always visible, always shows the selected pane. Window title = current pane name (single pane → "AppName Settings"). **Dim minimize & zoom**; window resizes to fit each pane. **Reopen the last-viewed pane.**
- Changes **apply immediately** — no OK/Cancel/Apply buttons (Mac convention; ⚠️ not stated verbatim in the current HIG, which says use the standard pane toolbar; every Apple Settings window behaves this way). Use `@AppStorage`/`UserDefaults` bindings.
- Keep settings few, good defaults; task-specific options belong in the UI where they act (View menu, inspector), not in Settings. **Don't duplicate system settings** (appearance/Dark Mode, accent color, scrolling, text size, accessibility) — follow the system. Detect, don't ask.
- Layout: SwiftUI `Form { }.formStyle(.grouped)` gives the System-Settings look (labels leading, controls trailing, mini switches); classic AppKit panes use right-aligned labels + left-aligned controls on a center line ⚠️ (legacy convention). Help button (?) bottom corner only.
- SwiftUI: `Settings { TabView { GeneralView().tabItem { Label("General", systemImage: "gearshape") } … } }` gives the menu item, ⌘, and pane toolbar for free; open programmatically with `@Environment(\.openSettings)` (macOS 14+) or `SettingsLink`.

**Choosing a presentation** (HIG Modality/Sheets/Alerts/Popovers/Panels):
| Need | Use | Mac specifics |
|---|---|---|
| Short task tied to one window that must finish or cancel | **Sheet** (window-modal) | Card attached to the parent window; parent dimmed; other windows stay usable. One sheet at a time; sensible default size, resizable if content benefits. Long/complex → new window or full screen instead. Buttons bottom-trailing: default (Return) trailing-most, Cancel (Esc/⌘.) to its left. ⚠️ HIG sheets placement updated Mar 24, 2026 — exact Mac text not in our copy. |
| Critical info / confirm an uncommon, **un-undoable** destructive action | **Alert** | Max 3 buttons; app icon shown automatically; optional suppression checkbox ("Don't ask again"), accessory view, Help button. Not at launch, not for info-only, not for undoable deletes. |
| Small, transient controls anchored to an element | **Popover** | Arrow points at source; closes on click-outside — **always save work on auto-close**; one at a time, never popover-from-popover, never for warnings; may be **detachable into a panel**. |
| Repeated input while watching results; tools for current selection | **Panel / inspector** | Floats; hides when app inactive; no minimize; not in Window list; menu text "Show Inspector" (no word "panel"). |
| Rich detail or second document | **New window** | Via File/context menu "Open in New Window". |

**Alert writing** (https://developer.apple.com/design/human-interface-guidelines/alerts): title says what happened + context, ≤2 lines, never "Error"/"Error 329347". Informative text only if it adds value. Buttons: 1–2 word **verbs** matching the title ("Delete", "Replace", "Don't Save"); **"OK" only for purely informational alerts**; never Yes/No; cancel button is always titled **"Cancel"**, never the default. Default button trailing; Cancel leading. Destructive style only when the destructive outcome wasn't the person's deliberate choice (Empty Trash's own confirmation is *not* red). To force reading, have no default button. Esc and ⌘. cancel. Caution symbol (`exclamationmark.triangle`) rarely. Don't explain the buttons. Prefer undo over "Are you sure?" (WWDC26 250: "use interruptions carefully"). Classic save-on-close pattern: "Do you want to save the changes made to the document "X"?" → Save (default) / Don't Save / Cancel ⚠️ (standard NSDocument wording).

**Launch & first run** (https://developer.apple.com/design/human-interface-guidelines/launching, …/onboarding): Mac apps need **no launch screen**; "launch instantly". Open straight into a useful window (last state, or a new untitled document / document browser). **Restore previous state** down to scroll position and window frames. No alert at launch (show offline state inline). Onboarding: optional, skippable, short, interactive, never repeated; contextual tips instead (TipKit works on macOS 14+). No license text, no system tutorials, postpone setup; ask for ratings/purchases only after engagement. Don't block first use on big downloads. Welcome window pattern (Xcode/Pages "New/Open/Recent") is fine for document apps ⚠️ convention.

**Privacy & permission prompts (TCC)** — HIG Privacy https://developer.apple.com/design/human-interface-guidelines/privacy:
- Ask **at the moment of use**, not at launch (unless the app is useless without it). Only what you need.
- Purpose strings (`NSCameraUsageDescription`, `NSMicrophoneUsageDescription`, etc.): one active, specific sentence, sentence case, ending in a period: "The app records during the night to detect snoring sounds." ✗ "Microphone access is needed for a better experience." ✗ "Turn on microphone access."
- Optional pre-prompt window: **exactly one button, titled "Continue"/"Next" (never "Allow")**, no cancel/close, no incentives, no fake alert images.
- Mac-only permissions **without a system Allow button** — Accessibility (`AXIsProcessTrustedWithOptions([kAXTrustedCheckOptionPrompt: true])`), Screen Recording (`CGRequestScreenCaptureAccess()`; or avoid it with ScreenCaptureKit's `SCContentSharingPicker`, macOS 14+), Input Monitoring, **Full Disk Access (no request API at all)**: show an in-app explainer saying *why*, *which* switch, and a button "Open System Settings…" deep-linking to the pane (`x-apple.systempreferences:com.apple.preference.security?Privacy_Accessibility` / `Privacy_ScreenCapture` / `Privacy_AllFiles` ⚠️ undocumented-but-common URLs), then **detect the grant** (poll / re-check on `didBecomeActive`) and continue automatically; tell people if a relaunch is needed (Screen Recording historically required one ⚠️). Never loop prompts. Sequoia+ re-confirms screen-capture access periodically (monthly per TidBITS https://tidbits.com/2024/08/19/apple-reduces-excessive-sequoia-permission-requests-shifts-to-monthly ⚠️ current behavior) — the picker API avoids it for user-chosen captures.
- Mac platform rules: sign with **Developer ID** + notarize outside the store; **sandbox** (required for Mac App Store); don't assume one signed-in user (fast user switching). Use Keychain, passkeys, Touch ID (`LocalAuthentication`) — never plain-text secrets.
- Login items: offer an "Open at Login" toggle in Settings (default off), implemented with `SMAppService.mainApp.register()` (macOS 13+); never silently add yourself ⚠️ (convention, not HIG text).

## 6. Controls, lists/tables, pointer, drag & drop, undo, documents, printing
**Control sizes — measured on macOS 26.3.1 Tahoe** (AppKit `fittingSize`, 2026-11-02):
| `controlSize` | Push button / pop-up / segmented / search field height | Checkbox | Label font |
|---|---|---|---|
| `.mini` | **16 pt** | 12 | 9 pt |
| `.small` | **20 pt** | 14 | 11 pt |
| `.regular` (default) | **24 pt** | 16 | 13 pt |
| `.large` | **28 pt** (capsule) | 18 | 13 pt |
| `.extraLarge` (new in 26) | **36 pt** (capsule) | 18 | 13 pt |
Text field (regular) 24 pt. HIG Accessibility: macOS default control size **28×28 pt hit area, minimum 20×20 pt**; ~12 pt padding around bezelled controls, ~24 pt around borderless ones (https://developer.apple.com/design/human-interface-guidelines/accessibility). Tahoe made mini/small/regular "slightly taller" than macOS 15 (WWDC25 310) → never hard-code heights; use stack views/Auto Layout/SwiftUI. Mini–regular = rounded rect, large/XL = capsule. **Don't mix sizes in one row; use style, not size, to mark the preferred option** (HIG Buttons https://developer.apple.com/design/human-interface-guidelines/buttons). Use **extra large only for the one hero action** (e.g. "Call", "Play"). Small/mini only in dense inspectors, palettes, status bars.

**Buttons** (HIG Buttons):
- **Push button** = the standard Mac button. Title-case verb label ("Add to Cart"); **append "…" when it opens another window/view needing input** ("Edit…", "Choose…").
- **Default button**: exactly one per window/sheet/alert; responds to **Return**, drawn with accent color (SwiftUI `.keyboardShortcut(.defaultAction)` or `.buttonStyle(.borderedProminent)`; AppKit `keyEquivalent = "\r"`). Never make a destructive action the default. Cancel button responds to Esc/⌘. (`.keyboardShortcut(.cancelAction)`; AppKit `keyEquivalent = "\u{1b}"`). Max 1–2 prominent buttons per view.
- Roles: normal / primary / cancel / destructive (destructive = red at *secondary* prominence in 26).
- **Square/gradient buttons** (+/− under a table, `bezelStyle = .smallSquare`), **help button** (round ?, one per window, bottom corner opposite dismiss buttons, never in toolbar), **image buttons** (~10 px padding around image; not in toolbars). Toolbar buttons are toolbar items, not bezelled push buttons. Always provide a pressed state for custom buttons; tooltips on icon-only buttons (`.help("…")`, `toolTip`).
- **Pop-up button** = choose one of several mutually exclusive values (shows current value); **pull-down button** = menu of commands (title stays fixed) — https://developer.apple.com/design/human-interface-guidelines/pop-up-buttons, …/pull-down-buttons. **Segmented control**: switch views in a toolbar/inspector, not in the main area (use a tab view there); tooltip per segment.
- **Toggles** (https://developer.apple.com/design/human-interface-guidelines/toggles): checkbox is the Mac default for options (supports mixed state, hierarchy via indentation); **switch** for emphasized settings that govern a group; in grouped forms use **mini switches** so rows align; don't swap existing checkboxes for switches; **radio buttons** for 2–5 exclusive choices. No switches/checkboxes in toolbars.

**Lists, tables, outline views** (https://developer.apple.com/design/human-interface-guidelines/lists-and-tables, …/outline-views): click column header to sort, click again to reverse; **resizable (and reorderable) columns**; alternating row colors for wide multi-column tables; outline view for hierarchy (hierarchy only in first column); column headers = title-case nouns, no colon; **middle-truncate** long names ("Quarterly…Final.pdf"); remember expansion state; Option-click disclosure expands all children; single-click a selected name to rename, double-click to open; **type-select** (type letters to jump), arrow keys move selection, ⇧/⌘-click extend; **Delete key deletes selection** (with undo); right-click acts on clicked row (even if not selected). Persistently highlight navigational selection; focused list uses accent-color highlight with white text, unfocused = gray (HIG Focus). Selection in inactive window = gray "background selection", still draggable. SwiftUI: `Table(rows, selection:, sortOrder:)` + `TableColumn`, `OutlineGroup`/`List(children:)`; AppKit `NSTableView`/`NSOutlineView` (`style = .inset`/`.fullWidth`, `usesAlternatingRowBackgroundColors`, `autosaveTableColumns`).

**Text fields** (https://developer.apple.com/design/human-interface-guidelines/text-fields): label + placeholder (placeholder isn't a label); width ≈ expected input; stack vertically with consistent widths; logical Tab order; validate on leaving the field, not per keystroke; number formatters for numerics; expansion tooltip for truncated text; combo box for text + suggestions; `SecureField` for passwords. Standard text views give spelling, substitutions, services, dictation, Writing Tools for free — prefer `NSTextView`/`TextEditor` over custom text engines.

**Pointer** (https://developer.apple.com/design/human-interface-guidelines/pointing-devices): arrow by default — **don't use the pointing hand for buttons** (pointing hand = links only); I-beam over text; open/closed hand for draggable canvas; resize cursors at edges/dividers; crosshair for precise selection; drag-copy (+) when ⌥ held; "operation not allowed" for invalid drops. SwiftUI `.pointerStyle(.link | .grabIdle | .frameResize(position:) …)` (macOS 15+); AppKit `NSCursor` + `addCursorRect`/`resetCursorRects`. Don't redefine system trackpad gestures; support swipe-between-pages, pinch zoom, smart zoom, force click (Quick Look/lookup) where they apply. Hover-revealed controls need a non-hover path (context menu / keyboard).
**Touch on Mac (HIG Oct 28, 2026)** — touch is a *secondary* input for "brief, intentional interactions": keep control size/density unchanged; standard gestures map tap=click, double-tap=open, one-finger slide=scroll, touch-and-hold=context menu, touch-hold-drag=drag (https://developer.apple.com/design/human-interface-guidelines/gestures). Hover-only controls: tap the area reveals them (not activates), keep selection, auto-hide after a few seconds; put essential hidden controls in the context menu; in a tabbed window a tap shows the selected tab's close button (https://developer.apple.com/design/human-interface-guidelines/pointing-devices). Custom gestures must work on touch *and* trackpad. Prefer gesture recognizers over `mouseDown` loops (WWDC26 289) so touch works.

**Drag and drop** (https://developer.apple.com/design/human-interface-guidelines/drag-and-drop): support it everywhere it's plausible, plus a menu alternative; move within the same container, copy across containers, ⌥ forces copy; drag image appears after ~**3 pt** of movement, translucent; highlight only valid targets; animate failed drops back; auto-scroll near edges; multi-item drag with count badge; **drag out to Finder** produces a real file your app can reopen (Calendar → .ics); drag from inactive windows without activating them; select-and-drag in one motion; spring-loading on toolbar/segmented targets; undoable; keep dropped items selected; offer multiple representations high→low fidelity, accept the richest. SwiftUI `.draggable(_:)`, `.dropDestination(for:action:isTargeted:)`, `Transferable`; AppKit `NSDraggingSource`/`NSPasteboardWriting`, `tableView(_:pasteboardWriterForRow:)`.

**Undo/redo** (https://developer.apple.com/design/human-interface-guidelines/undo-and-redo): top of Edit menu, ⌘Z / ⇧⌘Z, **unlimited** since document open/save, named ("Undo Move 3 Items"), scroll to/highlight what changed, coalesce slider drags into one step; no undo buttons in the UI unless essential. Prefer undo over confirmation alerts. SwiftUI `@Environment(\.undoManager)`; AppKit `NSUndoManager.registerUndo(withTarget:)`, `setActionName`.

**Documents & files** (https://developer.apple.com/design/human-interface-guidelines/file-management; the-menu-bar): use `NSDocument`/SwiftUI `DocumentGroup` — you get New/Open/Open Recent/Save/Duplicate/Rename/Move To/Revert To (Versions browser), **autosave**, the edited dot, title-bar proxy icon & rename popover, iCloud, ⌘N/⌘O. New docs are "Untitled" until saved. **Autosave periodically and on close/app switch**; show unsaved dot only when the user turned autosave off (System Settings › Desktop & Dock › "Ask to keep changes when closing documents") and then prompt on close/quit. Use the **system open/save panels** (search, tags, sidebar) not custom browsers; add an accessory view (format pop-up) in the save panel; hide extensions by default. Provide a **Quick Look** generator and **Spotlight** metadata for custom types; Finder Sync extension for sync status badges. Register UTTypes + document icons so files open in your app from Finder.

**Printing** (https://developer.apple.com/design/human-interface-guidelines/printing): File › Print… ⌘P (dim if nothing printable); system print panel; custom options as a named category in the panel; Page Setup… only for per-document page settings; remember settings with the document.

## 7. Typography, color, materials, Dark Mode, accessibility settings, SF Symbols, app icons
**Typography** (https://developer.apple.com/design/human-interface-guidelines/typography): system font **SF Pro** (SF Mono for code, New York serif); **macOS has no Dynamic Type** → body text **13 pt default, 10 pt minimum**; avoid Ultralight/Thin/Light. macOS text styles (also verified by `NSFont.preferredFont(forTextStyle:)` on 26.3):
| Style | Size/line | Weight (emphasized) | Style | Size/line | Weight (emph.) |
|---|---|---|---|---|---|
| Large Title | 26/32 | Regular (Bold) | Body | **13/16** | Regular (Semibold) |
| Title 1 | 22/26 | Regular (Bold) | Callout | 12/15 | Regular (Semibold) |
| Title 2 | 17/22 | Regular (Bold) | Subheadline | 11/14 | Regular (Semibold) |
| Title 3 | 15/20 | Regular (Semibold) | Footnote | 10/13 | Regular (Semibold) |
| Headline | 13/16 | **Bold** (Heavy) | Caption 1 / 2 | 10/13 | Regular / Medium |
Mac UI text is small: a sidebar row is 13 pt (medium sidebar size), table rows 13 pt, secondary labels 11 pt. Don't port iOS's 17 pt body to the Mac — it looks like a blown-up iPad app. Use `.font(.body)` etc. or `NSFont.systemFont(ofSize: NSFont.systemFontSize)` (13), `smallSystemFontSize` (11), `labelFontSize` (10); control-matching variants `controlContentFont`, `menuFont`, `toolTipsFont`, user document fonts `userFont`/`userFixedPitchFont`. Respect the user's per-app/system **Text Size** setting where supported ⚠️ (macOS 14+ Accessibility › Display › Text size affects some Apple apps; not a Dynamic Type equivalent).

**Color** (https://developer.apple.com/design/human-interface-guidelines/color):
- **Accent color**: define one in the asset catalog (`AccentColor`) — used for buttons, selection, sidebar icons — **but only when the user's accent setting is "Multicolor"**; otherwise the user's choice replaces yours everywhere (except deliberately fixed-color sidebar icons). Never hard-code `systemBlue` for selection; use `controlAccentColor` / `Color.accentColor` / `.tint`. Graphite accent also enables **desktop tinting** of window backgrounds — keep custom neutral backgrounds slightly transparent so they pick it up (HIG Dark Mode).
- Use **semantic dynamic colors**, never fixed hex for UI chrome: `labelColor`, `secondaryLabelColor`, `tertiaryLabelColor`, `quaternaryLabelColor`, `windowBackgroundColor`, `controlBackgroundColor`, `textBackgroundColor`, `separatorColor`, `gridColor`, `selectedContentBackgroundColor` (key) vs `unemphasizedSelectedContentBackgroundColor` (non-key), `alternatingContentBackgroundColors`, `keyboardFocusIndicatorColor`, `linkColor`, `placeholderTextColor`, `findHighlightColor`. SwiftUI: `.primary/.secondary/.tertiary/.quaternary` foreground styles, `Color(nsColor:)`, `.background(.background)`, `.foregroundStyle(.selection)` ⚠️.
- Liquid Glass color: glass has no color of its own; tint only the primary action/status (tint the *background*, not the symbol); colorful content → monochrome toolbars; never similar colors for labels and content.
- **Materials/vibrancy**: system sidebars/toolbars/menus/popovers already use materials — don't stack your own behind them (remove legacy `NSVisualEffectView` in sidebars). Custom: `NSVisualEffectView` (`.material`, `.blendingMode .behindWindow/.withinWindow`) or SwiftUI `.background(.regularMaterial)`; glass only for floating controls. Use vibrant label colors on materials. Clear glass only over rich media (https://developer.apple.com/design/human-interface-guidelines/materials).
- **Dark Mode** (https://developer.apple.com/design/human-interface-guidelines/dark-mode): support Light, Dark and Auto (switches while running). **Don't offer an in-app appearance setting** (HIG: "creates more work… may think your app is broken"; practitioner note: many pro/editor apps still add one — if you must, default to "System"). Separate light/dark assets in catalogs. Test with **Increase Contrast** and **Reduce Transparency**, separately and together; also Reduce Motion, Differentiate Without Color, and (macOS 27) **Show borders/button shapes**. With Reduce Transparency, system materials go opaque — custom translucent views must too (`NSWorkspace.shared.accessibilityDisplayShouldReduceTransparency`, SwiftUI `@Environment(\.accessibilityReduceTransparency)`); Increase Contrast → `accessibilityDisplayShouldIncreaseContrast` / `\.colorSchemeContrast == .increased`. Contrast target ≥ 4.5:1 for text (HIG Accessibility).

**SF Symbols** (https://developer.apple.com/design/human-interface-guidelines/sf-symbols): SF Symbols 7 (2025) adds **Draw On/Draw Off** animations and **gradient** rendering; rendering modes monochrome/hierarchical/palette/multicolor; variable color for levels; symbol effects (bounce, pulse, replace…). Symbols auto-match adjacent text weight/size — set `.imageScale`/`.font`, not frame sizes. Use standard symbols for standard actions (share `square.and.arrow.up`, delete `trash`, etc.; HIG Icons "Standard icons" table). Custom icons → custom symbol templates, not bitmaps. Menu bar extra icons = template images. **SF Symbols 8** (beta June 8, 2026, https://developer.apple.com/design/whats-new/) accompanies the 27 releases — ⚠️ its new features not reviewed here.

**App icons** (https://developer.apple.com/design/human-interface-guidelines/app-icons; WWDC25 "Say hello to the new look of app icons" https://developer.apple.com/videos/play/wwdc2025/220/):
- macOS 26+: icons are **square 1024×1024 px layered artwork masked by the system to a rounded rectangle** (same family as iOS); appearances: default, dark, clear light/dark, tinted light/dark. Build in **Icon Composer** (in Xcode 26+; `.icon` file): solid/gradient background + 1+ foreground layers (prefer SVG/PDF vectors; PNG for raster), let the system add specular highlights, refraction, shadows — **don't bake in shadows, bevels, glows, or pre-masked corners**; simple, filled overlapping shapes; avoid text and photos; no UI screenshots.
- The **classic Mac icon freedom is gone**: elements that used to break out of the shape (Contacts' tabs) must fit inside. Non-conforming legacy icons: if roughly rounded-rect, the system masks/extends them; if uniquely shaped, it **removes drop shadows and scales the artwork down inside the rounded-rectangle canvas** (practitioners call it "icon jail" — a gray squircle around a small icon ⚠️ term). Redraw instead.
- Bitmap-only icons get auto-segmented into 2 layers; text/thin lines don't receive glass. (HIG Oct 28, 2026 added "app icon format options" guidance.) 2026: Icon Composer supports multiple Liquid Glass layers & annotations; glass on icons is "sharper and more defined" in 27 (WWDC26 SOTU).

## 8. Keyboard & focus
- **Full Keyboard Access / keyboard navigation**: System Settings › Keyboard › "Keyboard navigation" (⌃F7 toggles) makes Tab reach all controls; with it off, Tab only visits text fields and lists. Test both. Also test Accessibility › Full Keyboard Access (⌃F1) (HIG Keyboards https://developer.apple.com/design/human-interface-guidelines/keyboards). The **Window menu Minimize/Zoom items exist for these users**.
- **Tab order** = logical reading order (leading→trailing, top→bottom); ⇧Tab reverses; ⌃Tab moves between control groups/out of tables. AppKit: `NSWindow.autorecalculatesKeyViewLoop = true` (or maintain `nextKeyView` yourself); `initialFirstResponder` for where typing starts. SwiftUI: `@FocusState`, `.focused($field, equals:)`, `.focusable()`, `.defaultFocus(_:_:)`, `.focusSection()`; macOS 14+ `.onKeyPress`.
- **Focus rings**: system draws them (`keyboardFocusIndicatorColor`, follows accent); text/search fields get a ring, list/table rows get a **row highlight** (accent when focused, gray when not) instead of a ring. Custom views: `focusRingType`, `drawFocusRingMask()`/`focusRingMaskBounds`; SwiftUI `.focusEffectDisabled()` only when you draw your own equivalent. **Never move focus without user action**; don't strip focus rings for looks (HIG Focus and selection https://developer.apple.com/design/human-interface-guidelines/focus-and-selection).
- **Key equivalents**: Return = default button, Esc / ⌘. = cancel/close sheet/popover/exit search; Space = activate focused control or Quick Look preview in lists; Delete/⌘⌫ = delete selection; arrows move selection/nudge; ⌘[ / ⌘] back/forward in browser-like apps; ⌘1…⌘9 switch sidebar sections/tabs (convention ⚠️). Every key equivalent should be visible in a menu (discoverability; Help search finds it).
- Menu bar extras/status items must work with keyboard navigation (Ctrl-F8 into status menus ⚠️): AppKit 27 `NSStatusItem` button target/action or `expandedInterfaceSession` for custom windows (WWDC26 289).
- Shortcuts display order ⌃⌥⇧⌘; prefer ⌘-letter; avoid ⌃; localize via system (SwiftUI `keyboardShortcut` with `localization: .automatic`).

## 9. SwiftUI for Mac snippets (+ AppKit equivalents)

```swift
@main struct MyApp: App {
  @State private var store = Store()
  var body: some Scene {
    WindowGroup("Library", id: "main") { ContentView().environment(store) }   // multi-window, tabs, auto state restoration
      .defaultSize(width: 1100, height: 700)
      .windowToolbarStyle(.unified)                       // .unifiedCompact / .expanded
      .commands {
```

## 10. What makes a "real Mac app" + common mistakes
**Apple Design Awards** (https://developer.apple.com/design/awards/; 2026 winners announced June 2, 2026 https://www.apple.com/newsroom/2026/06/apple-reveals-winners-of-the-2026-apple-design-awards/). Six categories with these official criteria: *Delight and Fun* ("memorable, engaging, and satisfying"), *Inclusivity*, *Innovation* ("novel use of Apple technologies"), **Interaction** ("Intuitive interfaces and effortless controls that are **perfectly tailored to their platform**"), *Social Impact*, *Visuals and Graphics* ("skillfully drawn interfaces… distinctive and cohesive theme"). Mac-relevant winners: 2026 apps — Guitar Wiz (Inclusivity), Moonlitt (Interaction), Tide Guide (Visuals); finalists Blippo+ (Panic, Mac), Structured. 2025 — Play by Rabbit 3 Times (Innovation; iPhone + Mac, a SwiftUI prototyping tool); finalists iA Writer, Mela (Interaction) (https://developer.apple.com/design/awards/2025/). Note: recent winners are mostly cross-device apps, not Mac-only productivity apps — one developer: "Agenda in 2018 may well have been the last truly Mac-assed winner" (Paulo Andrade, May 6, 2026, https://pfandrade.me/blog/mac-assed-swiftui-app/).

**"Mac-assed Mac app"** — Brent Simmons, Mar 19, 2020 (https://inessential.com/2020/03/19/proxyman): "a phrase I stole from my friend Collin Donnell to describe Mac apps that are unapologetically Mac apps. They're platform-specific and they're not trying to wow us with all their custom not-Mac-like UI (which often isn't very accessible)." NetNewsWire = yes; Slack = "most definitely not". Gruber, Mar 20, 2020 (https://daringfireball.net/linked/2020/03/20/mac-assed-mac-apps): better than "native" because "Native is ambiguous" — Slack may be native code "But it sure as shit is not a Mac-assed Mac app." Gruber on Panic's Nova (Sept 24, 2020, https://daringfireball.net/linked/2020/09/24/nova). Andrade 2026: apps that "not only native, but that also adopt the system's controls and conventions and integrate impeccably with the operating system's features" — menu bar heavy, lots of shortcuts, multiple windows, tooltips and hover states, AppleScript/Shortcuts, AutoFill. His SwiftUI pain points (still "not there yet"): selected-but-unfocused states (fix: `\.appearsActive`, track focus), arrow keys swallowed by `TextField` (use `.onMoveCommand`), drag sessions (drop to AppKit `NSDraggingSource`), toolbar coherence. Gruber, June 2026: "SwiftUI Only Makes It Easy to Develop Bad Apps" (https://daringfireball.net/2026/06/swiftui_only_makes_it_easy_to_develop_bad_apps) — test undo, focus, keyboard paths yourself.
**Practitioner conflict (2026):** Brent Simmons, "That About Wraps It Up for Stock Mac UI" (Sept 22, 2026, https://inessential.com/2026/09/22/that-about-wraps-it-up-for.html): dislikes Tahoe toolbars, full-height sidebars and glass buttons; stock-UI NetNewsWire took *more* work to adopt Liquid Glass than custom-UI apps; "we're left with no real reason to stick with stock Mac UI" (cites Things' non-NSToolbar toolbar). Gruber agreed (https://daringfireball.net/linked/2026/09/25/brent-simmons-stock-mac-ui). Also Prokopov "There's no native look anymore" (https://tonsky.me/blog/fall-of-native/). **This conflicts with the HIG** ("Avoid creating custom window UI…"). Agent guidance: custom *content* styling and a custom toolbar *look* are defensible; **never** drop the behaviors — menu bar completeness, shortcuts, standard traffic lights, focus/keyboard, undo, drag & drop, state restoration, accessibility, accent color, Dark Mode. "Mac-assed" is about behavior more than pixels.

**Tahoe critique to learn from** (all 2025–26): menu icons everywhere (fixed in 27); window corners that eat the resize area — ~75% of the grabbable corner was outside the window (Gruber Jan 12, 2026 https://daringfireball.net/2026/01/resizing_windows_macos_26; fixed 26.4 ⚠️); "lifeless" toolbars (Snell https://sixcolors.com/post/2025/09/macos-26-tahoe-review-power-under-glass/); legibility of glass (Six Colors Nov 2025; 26.1 added a Clear/Tinted choice); Tsai "Tahoe's Terrible Icons" (https://mjtsai.com/blog/2025/11/11/tahoes-terrible-icons/). Lessons: legibility > glass; icons need meaning; don't put interactive targets where corners clip.

**Checklist — a real Mac app:**
1. Complete, correctly ordered menu bar; every command (incl. toolbar/context/Dock items) present, with standard shortcuts, dynamic enable/disable, show/hide titles that flip.
2. Multiple windows where the content model allows; File › New Window/⌘N; Window menu lists them; native tabs for document apps.
3. Standard traffic lights, title bar, unified toolbar; resizable windows with sane min size; full screen via system.
4. State restoration on relaunch (windows, selection, scroll, panes); quits instantly.
5. Keyboard-complete: Tab order, focus rings, Return/Esc, type-select, arrow keys, ⌘, for Settings, ⌥⌘F search.
6. Undo/redo for everything that changes data; named; unlimited.
7. Drag and drop in and out (to/from Finder, other apps), copy/paste of rich + plain representations.
8. Settings window (panes, instant apply, remembers pane) — not a modal sheet or web page.
9. Follows system appearance: Light/Dark/Auto, user accent color, Reduce Transparency, Increase Contrast, sidebar icon size, scroll bar settings.
10. Context menus on every selectable thing, mirrored in the menu bar.
11. Uses system text views/fields (spelling, services, dictation, Writing Tools, AutoFill), system open/save/print panels, Share menu, Quick Look, Spotlight.
12. Small type (13 pt body), compact density, hover states + tooltips on icon buttons, arrow (not hand) cursor on buttons.
13. Automation: App Intents/Shortcuts (and AppleScript for pro tools ⚠️ optional), Services menu where relevant.
14. Proper icon (Icon Composer layers), Developer ID + notarized or sandboxed for MAS, Apple-silicon native.

**Common mistakes (AI-slop / port smell):**
- **iPad/Catalyst feel**: 17 pt text, huge rows, tab bar at the bottom/top instead of sidebar, single window, navigation push/back stacks instead of split views, sheets for everything, no hover states, no right-click.
- **Web-app feel**: hamburger menu, in-window "Settings" gear, custom title bar with fake traffic lights or none, pointing-hand cursor on buttons, toasts instead of inline status, modals with "×" in the corner, centered dialog overlays dimming the whole window, `<select>`-style dropdowns, no ⌘-shortcuts beyond copy/paste, links styled as buttons, text not selectable where expected (or everything selectable like a web page).
- Missing/empty menus (only App + Edit), commands only in toolbars or hidden behind gestures; "Preferences" naming or Settings without ⌘,; missing ellipses; hidden instead of disabled menu items.
- Modal overload: alerts for undoable actions, alerts at launch, sheet-on-sheet, onboarding carousels, permission prompts at launch.
- Custom window chrome or custom controls that ignore key/inactive states, accent color and Dark Mode; brand color everywhere instead of the user's accent.
- No state restoration; app opens to a splash/welcome screen every time; app blocks quit with confirmations.
- Glass on content or stacked glass on glass; tinted/borderless symbols mixed with bordered ones; overusing extra-large or prominent buttons; mixed control sizes in one row; icons on every menu item.
- Ignoring the notch/menu bar extras crowding; status-item apps with no Dock/Settings path to quit or configure.

## 11. Cross-platform shells on Mac (Electron/Tauri/Flutter/Qt) — Mac-specific must-dos
Everything above applies; these are the hooks that get you there (⚠️ API names from memory unless linked — verify against current framework docs):
- **Native menu bar**: Electron `Menu.setApplicationMenu(Menu.buildFromTemplate([...]))` with roles `appMenu`, `fileMenu`, `editMenu`, `viewMenu`, `windowMenu`, `role: 'help'` (+ `about`, `services`, `hide`, `hideOthers`, `unhide`, `quit`, `toggleDevTools` off in prod); accelerators `CmdOrCtrl+…`. Tauri v2 `Menu`/`Submenu` + `PredefinedMenuItem` (copy, paste, undo, quit, about, services, hide…). Flutter `PlatformMenuBar` + `PlatformProvidedMenuItem` (about, quit, servicesSubmenu, hide, minimizeWindow, zoomWindow, toggleFullScreen…). Qt: a parentless `QMenuBar` becomes the global menu; set `QAction::MenuRole` (`AboutRole`, `PreferencesRole`, `QuitRole`) so items move into the App menu automatically; use `QKeySequence::StandardKey`.
- **Window chrome**: keep real traffic lights. If you merge title bar and content, use Electron `titleBarStyle: 'hiddenInset'` (+ `trafficLightPosition`) / Tauri `titleBarStyle: "Overlay"` + `hiddenTitle` / Qt `Qt::ExpandedClientAreaHint` ⚠️ — and leave a draggable region (`-webkit-app-region: drag`), double-click-title-bar zoom behavior, and ~70–80 pt leading inset for the traffic lights ⚠️. Never draw fake ones.
- **Appearance**: follow `nativeTheme.shouldUseDarkColors` / `prefers-color-scheme`, user accent via `systemPreferences.getAccentColor()` (Electron) or CSS `AccentColor` system color ⚠️; `vibrancy: 'sidebar'` (Electron) / `window-vibrancy` crate (Tauri) for sidebars; respect `prefers-reduced-transparency`/`prefers-contrast`/`prefers-reduced-motion`. System font stack `-apple-system, BlinkMacSystemFont` → SF Pro at **13 px** base on Mac, not 16.
- **Behavior**: `cursor: default` on buttons (not `pointer`); disable text selection on chrome (`user-select: none`) but keep it in content; context menus via native `Menu.popup()`; Settings as a separate native window opened by ⌘,; Dock menu (`app.dock.setMenu`); tray → `Tray` with template image (`…Template.png`); remember window bounds (`electron-window-state`-style) and restore windows on launch; single-instance + `open-file`/`open-url` handlers; don't quit on last window close for document apps (`window-all-closed` → no quit on darwin); sign + notarize + hardened runtime; universal or arm64 build.

**Further reading:** HIG index https://developer.apple.com/design/human-interface-guidelines/ · WWDC25 310/323/356/219/220 · WWDC26 289/269/272/292/250 · macOS 27 release notes · Andrade's 2026 SwiftUI Mac article.
